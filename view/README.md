# The view

A VS Code extension: the list of changes in the sidebar, one page that shows a change as a diagram or as all its diffs, and a tab for each of its files with the whole file and its notes. The page fills its tab and uses the fonts and sizes of VS Code.

## Run it against a repo

```bash
npm ci && npm run build
code --extensionDevelopmentPath="$PWD" /path/to/a/repo
```

Install with `npm ci`, which takes exactly the versions of `package-lock.json`. The file `.npmrc` turns install scripts off (`ignore-scripts=true`), so no package runs code when it is installed. `npm run package` makes the `.vsix` with `vsce`, a dev dependency with an exact version, so its packages are in the lockfile too and `npm audit` and Dependabot see them.

Open "Apostil" in the activity bar and click a change. Cmd+Shift+. on the page or in a file tab turns the pointer into a comment icon, and the next click sticks a comment box there; on lines selected in an editor it asks in VS Code's input box. Set `APOSTIL_HOME` to read another store than `~/.apostil`. The code says "remark"; the page says "comment".

## The list

- **The list** puts the changes of one agent session under one head: the icon of the app and the name of the session as its link ("session" when no name is known), on one line, cut with dots when it is too long, with the full name in the tooltip. The `@` list cuts a long session name the same way. The name comes from the app's own files (`sessionName()` in `shared/agents.ts`), else from `apostil save --session-name`. Under a row, its pull requests (the icon of the state, then `#12 review needed`), loaded after the list is drawn and kept for 60 seconds; more than two in a session fold. A pull request in a stack has a quiet mark of its place ("2/3"), and its tooltip adds it ("#14 · Review needed · 2 of 3 in a stack"). Rows of one session whose pull requests are in one stack stand together, in the order of the stack, the top first. A click on one opens the page of its change at "Conversation". Each row has one state line: the agent is working, answers to read, remarks waiting, or what the row said before.
- **People on a pull request line.** The avatar of its author stands at its left, and its reviewers stand small at its right end, lying over each other, each with a dot in the colour of its state: three show, then a count ("+1"), in the order of the status strip of the page (`reviewerFaces()` in `media/tools.js`, which the strip uses too). A person with no picture is a round mark with the first letter of the login; a known product has its icon. The state words are cut with dots when the line is too short, so the row keeps its lines.
- **The search.** Under the row "Home" stands one field, "Search changes", with a clear mark and the icon "Sort and filter" at its right end. Typing filters the rows at once: a row stays when its branch, its agent app, or the number, title, author, a reviewer or a label of one of its pull requests holds each word of the text (no case). Filters are words in the field, as on GitHub: `author:<login>`, `reviewer:<login>`, `label:<name>`, `state:<state word>` (also `state:"no pull request"`), `agent:<app>` (`agent:claude`); a name with a space is quoted, an unknown word is plain text, and words of one key are "or", keys "and". One parser reads the field (`parse()` in `media/search.js`). Escape in the field empties it. The icon (a click, Enter on it, or Down in the field) and the command "Apostil: Sort and Filter the Changes" open "Sort and filter", **VS Code's own quick pick** at the top of the window (a view of the side bar is its own frame and can draw only inside it, so a menu in the view could not stand in front of "Files"). The view counts the values (`menuValues()` in `media/search.js`) and sends them with the search (message `menu`); `sort-filter.ts` makes the lines (the groups Sort, Author, Reviewer, Label, State and Agent, each with only the values that the rows have, their count in the description) and `sort-filter-pick.ts` shows them: an author and a reviewer have their avatar, a label a dot in its colour, a state a codicon in a colour of the theme, an agent the icon of its app. Each line has a check box; a click or Space on a line is one pick, and a pick writes its word into the field or takes it away (the sort that is on turns its order round, another sort replaces it). The list changes at once (VS Code sends the new search back to the view, message `search`, and keeps it), and the quick pick stays open with the line under the keyboard. Typing in it narrows the lines. Escape or a click outside closes it; so do Enter and "OK". The box "select all", the count of the checked lines and the button "OK" are VS Code's, and its API cannot hide them; "select all" does nothing. The sorts: modified (the default, newest first), created (newest first), author (A to Z) and size (lines added and removed, the largest first); a second click on the sort that is on turns it round. Modified is the latest of the last save of the change and the last update of its pull requests; created is the first save of the change (kept by the store since build 47, so an older change has none), else the creation of its oldest pull request, else the first commit of the branch (its author date). While a sort other than modified, newest first, or a filter word is on, the icon has a small dot.
- **The list while a search is on.** With an empty field and the default sort, the list is as before. With text, a filter or another sort it is one flat list of the rows that match, in the order of the sort, with no heads of sessions and no folds of rows ("History" rows match too); each row has the icon of its agent app before its branch. The line under the field says "3 of 12 changes", or "No change matches · Clear". A filter on pull requests shows only the pull requests of a row that fit it, and text that only some pull requests hold shows only those; text that the branch or the app holds shows the row as it is.
- **What is kept.** The text of the field and the sort stay when the list is drawn again and when the view is hidden and shown: the page sends each change to VS Code, which keeps it in the state of the workspace for each repo (`apostil.listSearch:<repo id>`), so it stays after a restart, and sends it back with the rows. What is unfolded is not kept.
- **Its data.** `gh pr list` gives the author, the labels with their colours, the reviewers asked (`reviewRequests`) and the newest review of each reviewer (`latestReviews`), and the dates of creation and update, in the same call as before. `pullRequestsFromJson()` in `shared/pull-requests.ts` maps them in one place, with `person()` and `reviewersOf()` of `shared/pull-request-facts.ts`, which the page of a pull request uses too. The list of gh gives no address of a picture: a person gets `https://avatars.githubusercontent.com/<login>?s=40` (a stand-in `gh` of a check can give `avatarUrl`); a bot and a team get none. `list.html` allows pictures from the same hosts as `page.html`. A row sends its dates as ISO values beside its age: `savedAt`, `firstSavedAt` and `firstCommitAt`. With no `gh` or no GitHub remote the search and the sort work on what the rows have (branch, agent, dates, sizes), and the quick pick leaves out the sort by author and the filters author, reviewer and label.

- **Open pull requests with no stored change** (build 69). Under the rows stands the quiet head "Pull requests" and one row for each open pull request of the repo whose branch has no row: its title, then its line (number, state, people). At most 20 show, then "n more" opens the rest. `readRepoPulls()` in `shared/repo-pulls.ts` asks `gh pr list --state open --limit 100` once (`repoPullsLater()` keeps the answer 60 seconds and adds the places in stacks); the view gets it as the message `repoPulls` after the rows. The search, the sort, the filters and the order of a look read these rows as any row (`pullAsRow()` in `list.js`). A click opens its page (`openRepoPull`, by its link, as "Apostil: Open pull request…"). When gh is missing, is not signed in, has no remote or fails, one quiet line under the head says why (`ghProblem()`: "gh is not signed in: run gh auth login"). The call runs on the side of the extension (`extensionKind` is `workspace`): in a remote window or a codespace that is the other computer, with its own gh and sign-in. The page of such a pull request says in one quiet line that it has no description of Apostil yet, with the words "Describe pull request #35 for Apostil" and a button that copies them. A click on the row of the open branch with no change file opens Home when it has no commit and no changed file against its base; with changes it opens nothing, as before.
- **A change that is not checked out** (build 69). `changeWhere()` in `shared/change-rows.ts` says where Git is read for a change: its own folder while it is a Git folder, else the open folder; when that folder is not on the branch of the change, the files, counts and diffs come from the commits from its base to the commit that the change was saved at (`changedFiles(folder, base, head)`), on the row, on the page and on the graphs page. The page says "as saved at commit abc1234; this folder is on main" in its summary line. When the clone has no such commit, the row and the page say so in one line and show no counts. A working tree is never counted for it.

## A pull request

- **Where it opens.** The page of a change whose branch has a pull request gets the view "Conversation" beside "Diagram · Diffs", and the state of the pull request in the status strip under the top line. A branch with more than one pull request shows the newest open one, and "1 more pull request" in the strip opens a small choice. A click on a pull request in the list of the side bar opens the page of its change at "Conversation". In the list each row shows its own open pull requests, two at most; its merged and closed ones are behind the fold of that row. One session shows at most two rows with an open pull request, and one line ("3 more pull requests") shows the others and folds them again ("Show fewer"). The row that is open now and a row with no pull request always show. A row whose pull requests are all merged or closed stands under the line "History · 2" at the end of its session, folded at first (`foldRows` and `foldPulls` in `media/states.js`). "Apostil: Open pull request…" takes a number or a link. A pull request of a branch with a stored change opens that page. Any other gets a page of its own with "Conversation" and "Diffs": its files in no part when its commits are in the folder, else one line with the command that gets them (`git fetch origin pull/12/head`) and its files with their counts from GitHub. A link to another repo gives "Conversation" and "Files". A number that does not exist names the tab "Pull request 999 not found" and offers no view. The line at the top holds the pull request as a step, "Pull request #12".
- **A stack of pull requests.** GitHub merges a stack from the bottom; each pull request targets the branch of the one below it. The stack is read with the pull request: its number, size and base, and for each pull request its place, number, title, state and draft. Its entries are read page by page too (`LIMITS.stack`, 200). Under the title stands "2 of 3 in a stack onto main", and beside the branches the pull request below ("`stacked-on-big → big-feature` · on #2"). The list of the stack has one row for each pull request, the top first: its state icon, number, title on one line, and "this one". In "Messages" it is folded into the line "2 of 3 in a stack onto main", and a click opens it; in "Classic" it is a box above the first comment. A click on another row or on "on #2" opens that pull request in the same tab, as a step of the path, so the line at the top leads back. As a file in a browser it opens `page.html?pull=pull-data-<number>.js`. The merge sentence of a pull request with an open one below it starts with "Waits for #2 below it in the stack"; the lowest one says what it says alone, and "The stack of 3 is ready to merge" when every open pull request of the stack is ready to merge. Joining or leaving a stack is a quiet row. The list of the side bar reads the places of all pull requests of the repo once, from `GET repos/{owner}/{repo}/stacks`. A page of a pull request with no stored change compares with its base, which for a stacked one is the branch below. A stored change of a branch on top of another branch says "compared with big-feature" in its summary line (`baseBranchOf()` in `shared/git.ts`). Creating, changing or merging a stack is not built, nor a diagram of a whole stack.
- **Reading.** `shared/read-pull-request.ts` asks `gh api graphql` (read only, 30 seconds at most for each call) and reads every list page by page; `pullRequestFrom()` turns the raw JSON into one plain object. The timeline is read from its end, so a limit keeps the newest items ("219 earlier items are on GitHub"). The checks are read page by page too. The limits stand in `LIMITS`: 1,000 timeline items, 300 threads, 100 comments in a thread, 3,000 files, 1,000 checks, 50 notes of a check. What a limit cuts off is counted, and the page says so with a link to GitHub; a cut list of checks never says "all passed". A second small query counts how far the branch is behind its base. On HTTP 502 or 504 the read starts again with smaller pages (50, 25, 10). A large pull request shows its head as soon as the first answer is there, with "Reading the conversation: 300 of about 900 items", and fills in the rest.
- **What comes with it** (`shared/pull-request-facts.ts`). Every check run (workflow, job, state, time, log, run page, notes on code lines) and every status of another product; of a job that ran twice only the newest run counts. The newest deployment of each environment. One sentence of what stands between the pull request and a merge, from what GitHub says: "Ready to merge", "Blocked: 2 checks failed · An approving review is needed · 3 commits behind main", "Auto-merge is on: …", "In the merge queue", "Merged by ines on 3 November with a squash", "Closed, not merged"; the hardest first. While GitHub does not know yet ("GitHub is still working it out"), the page asks again after 6 seconds, three times at most. Labels, assignees, reviewers with their states (a team, Copilot), the milestone, the issues that it closes, the tasks of the description. A commit has "Verified" when GitHub verified it, and names its author also with no account. Known products get their name and icon (`PRODUCTS`: GitHub Actions, Dependabot, Copilot); every other bot keeps its login and a quiet "bot" mark. A comment from a person's account stays that person's.
- **The state** follows the facts (`STATES` in `shared/pull-requests.ts`): "ready to merge" only when the review is approved, or in a repo that asks for no review when at least one check ran and all passed, and never while GitHub does not know about conflicts; else "review needed".
- **When it fails**, the page says why in one plain line and offers "Try again": `gh` is not installed, not signed in, no network or no answer in 30 seconds, no such pull request, no GitHub remote for a number, the rate limit (with the time it ends), a request too large for GitHub, an answer that is not what the code expects.
- **What GitHub sends is not trusted.** The HTML of a description or a comment goes into the page only through `cleanHtml()` in `shared/clean-html.ts`: an allow-list of tags and attributes, every text escaped. A link becomes `data-link`, which VS Code opens in the browser. A picture stays only over https from GitHub's hosts. A picture of a private repo is fetched by the extension with the login of `gh` and handed to the page as a data address (`shared/pull-pictures.ts`); the browser command does the same. A picture that does not load is its text and a link. A picture is at most about 360 px high; a click shows it large. A Mermaid block is drawn with the Mermaid of the page and its safe settings, and stays code when it does not parse. Text for screen readers only ("Loading") is left out.
- **When he last looked.** The store keeps, for each pull request, the time he last opened its conversation (`pull_request_look`). The page draws "New since you last looked · 4" above the first newer item and opens there; then the time is set to now. With no earlier time, or nothing new, it opens at the end.
- **The status strip** is one short line and says each fact once: the icon of the state (its word only for a draft and for conflicts), the reviewers as avatars that lie over each other, the first one whole and on top, each with a small dot in the colour of its state (the pointer says the name and the state; three show, who asked for changes first and a person before a team and a bot; the others are a count that names each one), the checks ("2 of 12 checks failed"; a click opens their list, which names the failed ones), and the first thing that still stands before a merge with a count of the others ("2 more"; the pointer on it says them all), without what the strip said before it ("1 check is still running · 5 commits behind main"); for a merged or closed pull request only who did it and when. The merge box of "Classic" keeps the whole sentence. A click on the checks opens their list under the strip: under the name of their workflow ("CI · GitHub Actions"), other products under "Other checks"; failed first, then waiting and running, the passed ones as one folded row ("7 passed"), skipped ones quiet. A failed check shows its notes with `file:line` (a click opens the file tab at that line), "View the log" and "Run again" (links to GitHub). The deployments stand there too ("preview: ready · staging: failed").
- **"Messages" is the modern look**: one column, a row with the avatar, the name and the clock time at the right edge, then the text; the date stands in the day lines ("Today", "Yesterday", "3 November") and in the tooltip of the time. Messages of one author within 5 minutes share one avatar. A heading at the start of a message is its title line. A review is a soft card with its verdict and icon, its threads under it. Events are quiet lines with a small icon; a run of one kind is one row ("3 force pushes on 11 November"), three or more events in a row fold into one row. A comment from a product is a compact row with its title and a fold; several in a row are one row with a count. Equal messages of one author are one, "posted 3 times". Reactions are small chips. The side facts are one quiet line under the title with "Details". More than 4 messages before the line fold into one row, drawn when he opens it. A slim bar with the state icon and the title stays at the top, and "↓ Newest" shows when he is not at the end.
- **"Classic" is the look of GitHub's conversation tab**: a line down the left side, a box for each comment with a head bar ("ines commented 3 days ago", marks "Author", "Owner", "bot", "edited"), events as small rows with their icon on the line (a commit with "Verified" and its short hash at the right, a label with its pill), a review as a row with its verdict and its threads as boxes, resolved and outdated threads folded with "Show resolved" and "Show outdated". The time always follows the words. More than 60 rows hide their middle behind "Show N more". At the end the merge box: the reviews in short, the checks with a fold for the list, the deployments and the merge sentence. At 1000 px and wider the side facts are a column at the right (Reviewers, Assignees, Labels, Milestone, Closes, Tasks); narrower, they stand under the title.
- **Threads**: a thread shows its file and lines ("whole file", "file removed"), its last 6 lines of code, and its comments. A long code line wraps and goes on at its indent plus 2 characters: nothing is cut off. The folded code lines are drawn only when he opens them.
- **The look on a dark theme** of VS Code: `look.css` has dark values of its colours under `body.vscode-dark`; labels take their own colour in a readable mix.
- **A long conversation**: the rows of the feed use `content-visibility: auto`, so only what is near the view is laid out, and the earlier messages are drawn only when he opens them.
- **The icon of a state** stands before every pull request: the list of the side bar, the status strip, the choice, the slim bar. `STATE_LOOKS` in `shared/pull-requests.ts` maps each state to its icon in `media/icons/` and its colour, beside the state words. When the pointer rests on an icon, or the icon has the keyboard focus, a small dark tooltip says "#12 · Review needed", in a stack "#14 · Review needed · 2 of 3 in a stack" (`Tip` in `media/tools.js`). The icon files stay as they are: `state-icons.ts` turns each into a data address for a CSS mask (`.pri` for the state, `.ico` for the others), so an icon takes its colour through `currentColor`.
- **Writing to GitHub** (`shared/write-pull-request.ts`). Nothing goes to GitHub unless the owner sends it himself, with a button or with Cmd+Enter in a field. No write happens when the page loads or a tab closes, and a failed send is never sent again by the code. Each kind of write is one GraphQL mutation through `gh api graphql --input -`: the query and its variables go to `gh` as JSON on standard input, so no text of a comment is on the command line. The reader learns what a write needs: the node id of the pull request and of each thread, whether he may answer, resolve and unresolve each thread, the lock, whether he opened it himself, and his review that is not sent yet with the count of its comments.
- **An answer in a thread**: in "Messages" and in "Classic" each review thread ends with a quiet field "Answer…". A click or Tab opens it to a few lines with the button "Answer" (Cmd+Enter). A thread that he may resolve has "Resolve" beside it; a resolved one has "Unresolve". After "Resolve" the thread stays open, so he sees "Unresolve".
- **A comment on the pull request**: the end of the conversation is a field "Write a comment…" with the button "Comment". The link to GitHub stays beside the title. Cmd+Shift+. in "Conversation" puts the cursor at the end of this field.
- **The review**: the strip of an open pull request has a quiet button "Review". It opens a panel under the strip: the text, the three verdicts "Comment", "Approve" and "Request changes", and "Send review". On his own pull request GitHub refuses "Approve" and "Request changes": they are not available, and their tooltip says "This is your own pull request." When he has a review that is not sent yet, the strip says "Your review is not sent: 2 comments", and the panel sends that review with its comments. A merged or closed pull request has no "Review". A locked conversation has no field, and one line says that it is locked.
- **A review that is not sent yet**: GitHub puts every new comment on code and every answer in a thread into it, where nobody else sees them until the review is sent. So the box on code and the answer field of a thread both say "This goes into your review that is not sent yet.", the strip says "Your review is not sent: 2 comments", and "Review" sends it with all its comments. (Seen with real sends: an answer in a thread did go into the review.)
- **Around a send**: while it runs the field is locked and its button says "Sending…". When it went through, the field is empty, the page reads the pull request again and shows the new item at its place, and the page keeps its place and the keyboard focus. When it failed (no network, no right, a lock, a line that GitHub does not take), the text stays and GitHub's own sentence stands under the field. A text that is not sent yet survives a redraw and a change of the view in the same window; leaving a field asks nothing.
- **In the example** (`page.html` as a file, and `?pull=`), a send shows the new item at once, marked "example", and nothing leaves the page. The browser check makes one send fail with `window.apostilExampleFailure`.
- **Not built**: "Viewed" on a file, editing or deleting a comment, reactions, a suggestion block, asking for a review again, labels, a merge, run a check again, update the branch (each is a link to GitHub), a thread beside the code in "Diffs" and in a file tab, Option+Right and Option+Left, a list of all pull requests of the repo.

## Links from outside

- **The handler** (`view/link-handler.ts`): `vscode://apostil.apostil/pull?repo=<owner>/<name>&number=<n>` (or `&branch=<branch>`) opens the pull request as "Apostil: Open pull request…" does; for a branch, its pull request asked of GitHub as the list asks, but in the repo of the link (`gh pr list --repo`), so that a clone of a fork finds it. `/change?repo=<owner>/<name>&branch=<branch>` opens the change of that branch, or Home and one line that it has no description yet. The repo is the open folder whose remote on GitHub is `owner/name`, also a remote other than origin; with none, one line offers to open a folder. A link only opens views.
- **The fields** (`shared/apostil-link.ts`): `repo`, `number` and `branch`, each checked (a branch as Git allows it, without `&`). A field it does not know is passed over, such as `url`, which `https://vscode.dev/redirect?url=…` adds on its way; so no field is named `url`. A link never holds a path of the computer.
- **The https form.** GitHub drops a `vscode://` link from its markdown, so every link outside VS Code is the vscode.dev redirect. `apostil link --pr [<number>]`, `apostil link --change` and `--markdown` print it (`store/link-command.ts`); `ICON_URL` is the address of Apostil's icon in the public repo, and the `--markdown` line starts with it. VS Code asks once whether Apostil may open links.
- **Source Control** has Apostil's icon in its title (Git only): it opens the change of the branch, as `/change` does.
- **The switch**: `apostil links off|on|status`, the commands "Apostil: Turn off links and nudges" and "… on", or `APOSTIL_NO_LINKS=1`. It is the file `links-off` in the store folder. While it is off, `apostil link` prints nothing and the icon of Source Control is gone.

## Home and the graphs of a path

- **Home**: the first row of the side bar ("Home" with the logo mark and the repo name) and "Apostil: Home" open the Home tab. It shows the top map of the repo (`apostil save-map`) as one surface that moves and zooms. A hover on a node lists its folders and files with their counts and the changes that touch it. In that window a folder opens in the tree "Files" of the side bar (`showInTree`) and a file opens in VS Code the normal way (`openFile`, as on the change page), so that it comes up with its notes as the setting says; this holds in every diagram of the map. A click on the node goes one level down, to the diagram under the map that covers the node, and the tree "Files" follows to the folders and files of that area while it shows. A node with no diagram under it stays on the map and leads to its code: one file opens, and folders open in the tree "Files", which then shows also when it was hidden. A click never opens the graphs of a folder: that page is behind the icon of a row of the tree "Files". A map written at another commit says "written 12 commits ago". With no map, the wordmark of Apostil stands large and quiet in the middle, where VS Code shows its own logo in an empty editor area. Under it: one line, the press "Map this repo with Claude Code" for each installed agent app with what the press does (`mapPressHtml()` in `media/tools.js`; a click starts a new session of that app, nobody types words into a chat; while it writes, the line of the map run stands in place of the press, see below); then the next step (`nextStepsHtml()` in `media/tools.js`): "Set up for agents" while no agent app sees the skills. "Write the map with claude-new": it starts a new session with the skill `apostil-map-repo`, which starts one writer for the overview and one for each large area (`startMapRun()` in `agent-run.ts`, the same spawn as a run for a comment), says that the agent is working, and shows the map when it is saved.
- **The map run that you can see** (build prompt 65): while a map is written, Home says which session writes it and what is saved so far.
  - *The record.* The store keeps one record for a repo (table `map_run`, `MapRun` in `shared/map-run.ts`): when the run started, the session that writes the map, and the parts saved so far (the overview, each area by its title, the notes of how many files, the groups of processes, the sets of marks). It is no file of the repo.
  - *How it starts and grows.* The first save of a writer that works (`save-map`, `add-diagram`, `add-notes`, `add-processes`, `add-marks`) starts the record when none is open, with the session of `agentFromEnv()`; each later save adds its part and its time (`recordMapSave()` in `store/map-run.ts`, called once in `runMapCommand()`; a save never fails for the record). No prompt of a writer names a session: the command reads it. The press of Home starts the record at once (`homeRun()`), and it takes the id of the session that the run reports on its output (`found` of `startMapRun()`: Codex at its start, Claude Code with its result) or that a save of its writers reads from the environment.
  - *How it ends.* At the save that leaves no work for the writers (`mapWorkLeft()`): no notes wait for the first process writers, `mark-groups` lists no group for any set, and `note-groups` lists no group. In a run of the whole skill that is the last `apostil add-marks` of Step 7, the service writers and the mark writers; the top diagram that Step 6 corrects is saved before it, and `apostil icon` after it saves no part of a map. A run that writes only a part of a map (notes alone, marks alone) is asked only for the kinds that it saved. The run of Home also ends when its program ends (`withEnd()` in `HomePages.writeMap()`): as a stop when it failed or saved no map. An open record with no save for 30 minutes (`QUIET_MS`) counts as stopped when the run writes the whole map (Home started it, it saved the overview, or it goes on after a run that stopped); a quiet run of a part counts as done (`mapRunState()`).
  - *The line.* `mapRunLine()` makes the words once, and `homeData()` gives them to Home as `mapRun` (`mapRunOf()`, with the name of the session from the files of its app). "Writing the map · Claude Code session 1a2b3c4d · overview, 3 of 8 areas, notes of 40 files", with the whole id and the titles of the areas in the tooltip. "8 areas" are the areas of the top diagram; not each gets a diagram of its own. A session of the Claude desktop app has the quiet link "Open the session" (`claude://…/<hostSession>`, only an id); a session with no link has the command that resumes it as text, which one click selects. The run of Home is "a session with no window" and has no link; no log of it is kept. The line stands in place of the press while the repo has no map, and after the words of the summary line when the map shows (`mapRunHtml()` in `media/tools.js`); nothing in it moves, and it goes when the run is done.

## Marks and the look of a repo

Build prompt 51. One mechanism for both: **marks** are icons at lines of code, written by agents and rolled up to the notes, steps and nodes that hold the line; a **look** is a list of rules that a user asks for in plain words and an agent saves for one repo. With no look saved, every page is as it was, and the default look shows the marks of the built-in set `services` (the services that the code reaches) at the upper right of a node, a step, a call out of the repo and a note.

- **Marks** (`shared/marks.ts`): the map holds `marks` (set, value, file, line, a word on the line, the text of the line at the save; for a service also a relation `calls`, `stores`, `sends` or `runs on`, and a named thing `{ kind, name }` when the code names it with fixed text) and, by set, the files that a writer read (`markedFiles`). `apostil add-marks` saves the marks of one group for one set and replaces only what that group saved for that set and the files that it names; a value is known in the set or declared once in the same JSON (a service with its name and web address, never a second id for one address); an icon (PNG, SVG, ICO or WebP, at most 100 KB, an SVG with no script, no event attribute and no outside address) is kept in the store by set and value (`icons/<set>/<value>.<ending>`), so another repo needs no new fetch; the values themselves are kept in the table `mark_value` for every repo. Its draft `apostil-marks-<group>.json` and the icon files `apostil-icon-<value>.<ending>` in the top folder are removed after a save that worked, and `apostil setup` keeps them out of Git. `apostil mark-groups --set <id> [--all]` gives the work by area, only the files that need it (no writer of the set read them, their text changed since, or a mark of them no longer stands); for `services`, only the files with candidates, each with its candidate lines from one short list of signs (`SIGNS` in `shared/marks.ts`). `apostil marks [--set <id>]` prints the counts of each set and value, the marks whose line changed (hidden until the next run, by the rule of notes beside the code) and the icons that a website refused (`iconRefused`), and `noIcon`: the services with marks and no icon. A save of the map keeps the marks. **Icons** (`store/icon.ts`, `shared/icon-fetch.ts`): `apostil icon <service id> <https address> [--site <site>] [--other-site]` is the one command that reaches the web. It keeps the picture as the icon of the service; https only, the host is the `site` of the service or a host under it (a redirect too; `--site` names the site of a service that the next `add-marks` declares; `--other-site` only after the owner said yes), at most 100 KB of a kind that an icon may be, 10 seconds; the address of a web page gives its `link rel="icon"` or `"apple-touch-icon"`, the largest that fits. It prints `{ saved, problem }`. A service of a draft with marks, and no icon, no waiting icon and no `iconRefused` entry, is refused by `add-marks` with a sentence that says to run `apostil icon`. **`apostil map --fit`** (`shared/map-fit.ts`) prints three lists of at most 20: files with notes in no node, nodes that hold no file with a note or a process, and calls of the processes between two nodes of the top diagram that have no arrow (each with an example); the skill corrects the top diagram from them (Step 6).
- **The look** (`shared/look.ts`): `apostil set-look` saves the look of the repo in the store (table `repo_look`, its files in `looks/<repo id>/`); `apostil look` prints it, or that the default applies. **One list**, `LOOK_PARTS`, holds every component that a look can change, its slots with their fields and the kind of value of each field, what a rule can pick, every target of a click, and the form of a new set of marks; the check of `set-look`, the files of a look and `apostil look-slots` all read it, so a later build adds a component, a slot or a target there, with its `area`, its `what`, its `words` and one `example`. A look has `sets` (more mark sets: id, name, rule for its writers, values, the corner where it stands on a node and on a note) and `rules`. A rule picks a kind (`node`, `step`, `call`, `arrow`, `note`, and since build 60 the parts of the page of a change and of the file tab, below) and any of paths, node ids of a diagram, a mark (`set:value` or `set:*`) and a diagram id, and sets slots: `box` (colour, line colour, line width, dashed, shape), `content` (words, a picture or a film), `corners` (a set, a button with an action, or nothing), `note` (colour) and `arrow` (colour, width, dashed, a button at its label). The default look is the first rule, then a rule for the corner of each set, then the rules of the look (`lookRules()` in `look-data.ts`); for each slot of a thing the rule that names it most closely wins (a node id, then a mark, then a path, then a kind), then the later one (`resolve()` in `media/marks.js`). `set-look` checks kinds, slots, paths, node and diagram ids, colours, shapes, sets, targets and files (a picture at most 2 MB, a film at most 20 MB, standard types), and keeps each file named by its contents.
- **How the options reach the agent** (build prompt 56): the agent reads them in layers, and only when the owner asks for another look. The prompt of the look writer says how a look works and holds no list of parts. `apostil look-slots` prints the core and one index line for each area (`areas` in `LOOK_PARTS`: diagrams, processes, notes, marks, clicks, windows, lists, and of build 58 blocks and pages, of build 60 change, diffs, comments, file-tab, of build 61 side-bar, pull-lines, files, pull-request, conversation, of build 59 home, drawings, graphs, panel-lines, of build 62 vscode); the core is what most looks use, marked `core` in the list (the box, the arrow without its button, the colour of a note, the corners, every pick, the forms of the five targets of build 51, and of build 57 `show.shown`, `content.words` and `click`; a component lists only its core slots there). An area prints a slot of another area as one line that names that area. `apostil look-slots <area>` prints one area: its components with their slots and examples, the fields with the kinds of their values, and the names of the picks; a slot comes with only the fields that the components of the area take (`takes`), and only the kinds of those values. `apostil look-slots --find "<words>"` prints the 5 best matches over the names, the `what`, the `words` and the examples (small letters, whole words and starts of words, a hit in a name counting most; no model), and with no match one sentence and the index. `apostil look-slots --all` prints the whole list. The answers are printed with each short part on one line (`compactJson()`), and their sizes are a contract that `store/look-options.test.ts` holds: the prompt and the answer with no argument at most 9,000 characters, each index line at most 110, one area at most 3,000, one search at most 2,000 (`shared/look-slots.ts`); an area that passes 3,000 is split in two, as build 61 split the side bar into `side-bar`, `pull-lines` and `files`, and the area of the pick "where" lists the fields of the components of the core only. The list also holds what no look can use (`never`: a line above code, words in or after a code line, a tint of lines, a hover over code, a badge in the Explorer, the status bar, marks in the scroll bar, the Timeline, links in the terminal, the path above the code, the outline, inlay hints, problems under code, badges in Source Control, a count on Apostil's icon, comment threads in code, status items of notebook cells, the Testing view), each with the words that a person may use for it: when such words fit it better than any part, `--find` answers one sentence ("A look cannot use the status bar. Tell the owner so."), and a rule whose kind names it gets one sentence too. `apostil set-look --check <look.json>` checks all that the save checks, the files too, and saves and removes nothing; it prints `{ ok, problems, changes, notes }`. `changes` says for each rule how many things it picks now and what it gives them ("Rule 1: 2 nodes get a colour."), with the pick logic of the pages (the first part of `media/marks.js`, read in Node) on the diagrams of `homeData()` and the notes of the map (`store/look-changes.ts`); `notes` names each rule that picks nothing now, which is no fault. `set-look` prints the same after a save. Each sentence about an unknown name (a kind, a slot, a field, a pick, a shape, a target, a set, a diagram, a node, a command, an area) ends with the nearest right name when one is close: one or two letters changed, the same first three letters, or a name of several words that holds the word ("failing" in "checks failing"; `nearest()` in `shared/look.ts`).
- **The drawing** (`media/marks.js`, one path for a mark of any set): Home and the drawn processes apply the look when they draw (`look` in the data of Home, from `look-data.ts`: the rules, the sets, the values with their icons as data addresses, the marks that stand, and an address for each picture and film). A shape and other words go into the Mermaid text before it draws; a picture or a film takes Mermaid's picture shape with a blank picture of its size, and the real file goes in after the drawing, never into the text; the page treats `g.image-shape` as a node (`markDiagram`, `lightNodes`, the clicks and windows of Home). A film shows a frame with a play mark and plays, muted, only on a click. A missing file gives back the default box. One colour gives the colours of both themes and of the words (`boxColors()`, `lineColors()`): a pair whose words would not read at 4.5:1 is moved until they do; a high-contrast theme keeps its own colours. A diagram that the look does not change is drawn exactly as before.
- **Marks on a node**: a node holds the marks under its paths, a step those inside its lines, a call out of the repo those at its lines; the step that calls gets no second chip for them. An arrow of a process shows a mark at its own line, unless one of its two ends shows that mark already (the call box of that service, or the step that holds it in a corner): one service has one icon there, and the window of the end lists the use at the line of the arrow (`arrowMarks()` in `media/marks.js` decides it; a rule still picks an arrow by every mark at its line). A corner shows at most 3 chips, then "+n", the values that few nodes of the diagram hold first. An icon stands on a small light round chip in both themes; an icon that fills its square is drawn to the edge of a rounded square; a value with no icon gets the first letter of its name. The pointer on a stack spreads it and opens its window (each value, its places, what the code does with it, its named things: 2, then "+n"). A click on a value goes down one level when the node has one, with the nodes that hold the value lit and the quiet line "<value> · n places in <node> ×" (the line at the top names the step); else one place opens at once, and several are listed by named thing. A set that stands in no corner of a node is listed in the window of the node. A button does its action: a file at a line, a web address after VS Code asks, a command of Apostil, a prompt to a new session of the first agent app, or a place in Apostil (a diagram of the map at a node, or a drawn process).
- **Notes**: the note cards of a file tab and the window of a step have the corners of their sets, the colour of the look as a bar, and one line for each service ("PostgreSQL · keeps data in it · 7 places") with its named things as small links (7, then "+n more"). The marks of a file come with its code (`marksBeside()` in `page-data.ts`), with their lines now.
- **The shared kinds of every component** (build prompt 57). Each is built once and every component that takes it uses the same code.
  - *Fields.* A component lists its `fields`, what a rule can read of a thing from the data of the page: a node `title`, `files`, `down`; a step `title`, `file`, `steps`, `is` (step or process); a call `name` (the names that the code calls it by), `of`; an arrow `words`, `of` (the node it comes from); a note `title`, `file`, `function`, `tests`. The pick `where` (`{ "<field>": <value> }` or a list of values) picks by them and ranks after a path and before a kind. `takes` names the fields of a slot that a component takes; the check says so in one sentence ("a node cannot be folded. A node takes only "shown"."), and a wrong name gets the nearest right one (`nearest()`).
  - *What shows and the words.* `show.shown: false` leaves a node, a step, a call or an arrow out of the Mermaid text with its arrows before Mermaid draws (`shownFlow()` and `flowWithout()` in `media/marks.js`, which count the arrows as `flowGraph()` does; a statement that names nothing hidden stays as written, and a group left empty goes), and a note card out of the column of notes; counts elsewhere keep counting it. `content.words` may hold fields in braces (`"{title} · {files} files"`, `fillWords()`; text from the repo is escaped), also on an arrow, and `content.fields` orders the fields of a note card (title, function, tests, text, services) and leaves out the others. `text` gives the words a colour (an arrow), a size (small, normal, large) and an icon before them (a node, a step, a call): the size and the place of the icon are Mermaid classes there while it measures. `order` (by, down, group, first) and its one function `orderRows()` order the rows of a list; a list takes each field of `order` that a rule gives one of its rows (`listOrder()`), and `shownInOrder()` gives the rows that a list shows in that order (build 60: the files of the list of diffs, the threads and the open points, the views, the diagrams of a part, the notes; build 61: the rows of the list "Repo", the folders of the tree, the checks, the side column, the look of the conversation; build 59: the panels of the graphs page).
  - *One list of targets.* `LOOK_PARTS.targets` (build 51 called them actions; a button keeps its field `action`) holds every place a click, a key or a menu entry goes: `file`, `url`, `command`, `prompt`, `place`, `graphs`, `folder`, `change` (with `part`), `pull` and `comment`. A command is one of `LOOK_COMMANDS` (the commands that open or change a view); the save refuses the commands that set up agents, install the command, connect Claude Code, uninstall or turn links off and on, and the extension runs no other. One `act()` in `media/marks.js` serves every page: the comment box opens on the thing, a place or the graphs of a path open as a step of the path when the page can take it (`Marks.useHere()`), and the rest goes as one message `target` to one function in the extension (`answerTarget()` in `look-targets.ts`), which asks before a web address opens and shows a prompt whole with "Send" before it goes, also from a note card. `package.json` declares no `capabilities.untrustedWorkspaces`, so VS Code keeps Apostil, and every look, off in a workspace that it does not trust.
  - *A click and other input.* `click` is one target in place of today's click (a node, a step, a call, the words of an arrow, a note card). `input` has `alt` and `shift` (a click with that key held), `double`, `key` (a letter or a digit while the pointer is on the thing or it has the keyboard; the keys that a page uses already, `PAGE_KEYS`, are refused with the free ones) and `menu` (rows of a small window on a right click, in the frame of `hover-window.js`). Only a thing with a double click waits a quarter of a second before its single click (`bind()`). The pointer says what a click and each other input do, one line each (`inputWords()`): at the top of the window of a node or a step, and in a small window on the words of an arrow and on a note card.
  - *The window of the pointer.* `windowOf()` builds a window from named sections; `nodeWindow()`, `noteWindow()` and `stackWindow()` use it. A node has `files`, `changes`, `marks`; a step and a call `note`, `where` (the quiet line of the title), `marks`. The slot `window` gives a `width` and the `sections` in their order; a section that it does not name is not shown, and a section of its own (`{ "title"?, "blocks" }`, build 58) stands at its place among them, outside the frame of the sections of today (`ownSection()`).
- **Blocks, windows of blocks and pages of the look** (build prompt 58). A look says *what* a window or a page shows with blocks, and Apostil draws them in its own style, in both themes; the agent writes no HTML and no script, and blocks stand only in Apostil's own pages and windows, never in VS Code's editor.
  - *The blocks* (`LOOK_PARTS.blocks`, each with its `what`, its `form`, and `file` when a file of the repo may take the place of its value; `blockTitle`, `sources` and `limits` beside them): `text` (paragraphs, no HTML), `fields` (names with values), `table`, `bars`, `code` (never cut off; from a file the name of the file opens those lines), `state` (a dot, a word, quiet words), `links` and `button` (each to a target of the one list), `picture` (kept in the store as the picture of a node is), `diagram` (a diagram of the map, small, drawn by `drawPanel()` of the graphs page; a click opens it on Home) and `row` (two or three blocks side by side, one under the other when narrow; no row in a row).   - *A window as a target.* `{ "window": { "title"?, "width"?, "blocks" } }`: `Marks.act()` opens it at once beside the thing, in the frame of `hover-window.js` (`Hover.now(…, asked)`, which opens also from a row of a menu); it closes as a window of the pointer closes, and every window of the pointer now also closes with Escape.
  - *Pages of the look.* A look has `pages`: `[{ "id", "title", "blocks" }]`, at most 20, each id once. The target `{ "page": "<id>" }` opens a page as a tab, as the graphs of a path open (`HomePages.openPage()`: one tab for one page, named by its title, with Apostil's icon): `home.html` in the kind `page` (`CustomPageData`, `pageData()` in `look-blocks.ts`), a step `{ tab: 'page' }` of the path, so the line at the top says "Home › <title>".   - *Limits*, all in the list: a page at most 30 blocks; a section of a window and the window of a target at most 6; a window at most 4 sections of its own; a table at most 50 rows (10 when the rule gives none) and 12 columns; a code block at most 100 lines; a file at most 2 MB; a look at most 20 pages. - **The page of a change and the file tab** (build prompt 60). `lookOfPage()` in `page-data.ts` gives the look of the repo to the whole page and its file tabs, also for a repo with no map (its look has no marks then); a kept file of the look gets an address of the webview, so a picture can stand in place of a step. ## Notes beside any code file

- **A code file that opens the normal way has its notes**, with no click: the editor of VS Code stays as it is, and the notes stand in it. A note shows when its lines are still in the file with the same text. The notes come from every described change of the repo, open or merged, also after the branch was squashed and deleted. One rule finds them, with no `vscode` import: `shared/notes-beside-code.ts`. The editor, the file tab and the tests all use it.
- **The rule**: the save keeps the text of the lines of each note (`noteCode` of a stored change). For a file, the rule looks for those lines in the text as it is now, as one block with the same text; spaces at the end of a line do not count. When the block is there more than once, the place nearest to the old line numbers counts. When it is not there, the note is older than the code and does not show. A change saved before the save kept the text reads it from Git at the commit of its save, while Git has that commit; else its notes do not show. The same note from two saved changes (a stack, a branch saved again) shows once, the newest. The text in the editor counts, also lines that are not saved yet: after an edit the notes move with their lines. When the cleanup removes a change, the store keeps its notes and their text (`kept_notes`), so they still stand beside the code.
- **In the editor of VS Code** (`notes-beside-code.ts`): the title of each note as quiet text, with no box, at the end of the first line of the note. A file can have 40 notes and more, with a step inside its function, so the editor stays calm: one title on a line, and one marked note at a time. The pointer on a line shows the narrowest note that holds it (a step, not its function), and on the first line of a note also that note: its title, its text, its function and its test count, its linked tests, the change or the map it came from, and "Open in the file tab of Apostil". The note under the pointer gets a thin teal line at the left of its lines; no other note has one (`markOf()`). The colours are theme colours of the extension (`apostil.noteLine`, `apostil.noteTitle`), with values for light, dark and high contrast; a theme can set its own.
- **The line of the title**: the first line of the note. When notes start on one line, only the narrowest has its title there; the pointer on that line shows the others too (`titledNotes()` and `notesAtLine()` in `note-lines.ts`). A title longer than 60 characters is cut; the pointer shows the whole note.
- **Cmd+Shift+,** (Ctrl+Shift+, elsewhere; the key beside the comment key) hides the notes of this tab and shows them again. It holds for this tab only: when the tab closes, the file opens with its notes the next time. The key works only when the file in front has notes; else VS Code's own command of that key ("Replace with Previous Value") stays. A quiet count in the status bar says "4 notes", "4 notes hidden" and "1 older than the code"; a click on it does what the key does. A file with no notes shows nothing of Apostil.
- **The setting `apostil.notesBesideCode`**: `tab` (the default) opens a file that has notes in the file tab of Apostil by itself, with each note as a card beside its lines, unless the file has edits that are not saved; the key changes that one tab to the editor and back, and the file tab then opens at the line he was on. A file that opens at a line (a search result, "Go to Definition", a line after its name in Quick Open) opens the file tab at that line: the tab opens at the line known at once, and a place of the cursor that VS Code tells a moment later goes on to the tab while the editor still stands (`follow()`), with no wait. The start of a file tab (its lines, or its first or last change) stays with its view until its page is ready (`takeStart()` in `page-data.ts`): a load of the data while the page still loads does not use it up. A notebook is the one file that keeps its own editor with `tab`, with its notes in its cells, because the file tab cannot run a cell. `editor` is the compact way: it puts the notes into the editor of VS Code. `off` shows no notes beside the code.
- **What the editor of VS Code does not let an extension do**: place a view beside the lines of its editor. So there is no column of cards at the height of their lines, no line from a note to its code, no arrow from note to note, and a title is one line of text with no wrap and no font size of its own. The stable interface gives text after a line, a line mark, a mark at the right edge, a hover and the status bar; Apostil uses those, and no proposed interface. The column waits for the fork.
- **A notebook in the notebook editor of VS Code**: a notebook that opens the normal way shows its notes in its cells, with the same marks: each cell has a text editor of its own, and the marks of a note go into the editor of the cell that holds its lines. The rule reads the notebook as the text of its cells (`shared/notebook.ts`), from the notebook editor with the cells that are not saved yet, so a cell put in above moves the note with its cell. The pointer on a noted line of a cell shows the whole note, with "cell 5, lines 2–3". The key, the count in the status bar ("2 notes", for the whole notebook) and the setting hold as for a code file; with the setting `tab` a notebook stays in the notebook editor until the key. Nothing of Apostil starts a kernel, runs a cell or changes the notebook.
- **What the notebook editor does not let an extension do**: a text cell (Markdown) shows as a formatted page and has no text editor until it is edited, and the stable interface gives no mark on that page; so a note on a text cell shows only while that cell is edited (a double click), and the count in the status bar still counts it. The marks of a note in a code cell are the marks of a code file; a note whose lines run over two cells is marked in each.
- **Not built**: notes on a file that is not in a Git repo, and notes in a diff editor of VS Code.

## The file tab

- **A click on a file name** opens the file as a tab of its own in the group of the page: a read-only custom editor (`apostil.file`, priority `option`) for the real file, so the tab has the file's name and icon. A second click shows the open tab. A file that the change removed stays on the change page.
- **The whole file, nothing above it**: every line, as in an editor; added lines have the added background, and the lines that the change removed stand in place with the removed background. Only the rows in view are drawn, inside a block with the height of the whole file, so a file of 7,500 lines opens at once and its scroll bar is right from the start. Code is never cut off, and nothing scrolls sideways: a line longer than the box of the code wraps, at any character, and goes on at its indent plus 2 characters. The line number and the sign stand beside the first visual row. Tabs are 4 wide.
- **Rows of different heights**: the font is monospace, so the visual rows of a line follow from its length and the width of the box (`Wrap` in `code-notes.js`); the width of one character is measured once. `virtualRows` adds the heights up: the top of a row is the sum of the heights above it. The scroll to a line, the change in view, the place of each note and its join all use these sums. A row that is drawn taller than worked out (a wide character) keeps its real height. When the box gets another width, the heights are worked out again and the line at the top of the view stays at the top (`Code.fit`).
- **The small code map** (`codeMap()` in `media/code-map.js`) stands at the right edge of the box of a whole file, left of its scroll bar, as VS Code has it beside its editor: each row of the file is a row 2 px high, each piece of it a bar 1 px wide for each character, in the colour that the code view gives it (the pieces are read from the same coloured HTML, `lineColors()`), wrapped as the code wraps. Its places come from the sums of `virtualRows`: the map is the box of the code at a scale of 2 px for one row. It is drawn on a canvas, and only the part that shows. The part in view is a soft box (the colours `minimapSlider` of VS Code, at half strength at rest), stronger under the pointer and while it is held; a click shows that place in the middle of the box, a drag of the box scrolls, and a wheel on the map scrolls the file. A file taller than the map moves the map with it, so its top shows at the top of the file and its end at the end. A thin teal mark at its right edge stands for the rows of each note, and added and removed rows have the faint colour of their rows. Wide, the map is 120 px and lies under the right end of the column of the notes: the cards lie over it, whole, with their lines; where no card stands, the map shows, and the last 10 px at its right always show. The column keeps its width, so the code keeps its width. Narrow, the map is 60 px at the right of the marks, so no mark lies on the map. A file with no notes has the map in a column of its own. It sticks below the control of the files. With the setting `editor.minimap.enabled` of VS Code off there is no map; the extension sends the setting with the data of the page, and a change of it shows or hides each map in place (`minimap`). The file beside the diagram of a part and the file of "Diffs" are the same file view, so they have the same map.
- **"Edit"** in the control of the files at the top right changes the tab to the editor of VS Code, at the first line in view, with the keyboard in the editor; a double click on a line does it at that line. It is the same change as Cmd+Shift+, (`apostil.toggleNotes`, which takes the file and the line), and the key brings the file tab back at the line of the cursor.
- **The notes** stand in a column beside the code, each at the height of its first line, and never over the code (`cardPlaces()` in `code-notes.js`, one rule for the file tab, "Diffs" and the page of a part). Where the cards of a stretch do not fit at their rows (a note for each 4 lines), they show their title on one line; the pointer on a card or on its rows opens it to its whole text over the cards below it, and no other card moves. Where even the titles do not fit, a card stands lower than its row. A line joins each note to the middle of its code lines. A step inside its function (a note whose lines lie inside another note) stands one lane in under the card of its function, and the card of the next function stands at the left again; the function is the head of its steps, and its line joins its first row only (`lanesOf()`). The notes of one function in a change are its numbered steps: an arrow goes from each to the next (`noteLinks`). The pointer on a note lights its lines and its line, and the pointer on lines lights the narrowest note that holds them (`narrowestAt()`): a row of a step lights the step, a row of the function in no step lights the function. The box of the code ends where the notes begin. A note of a wrapped line stands at the first visual row of its first line. The first note of a function names it with its test count ("3 tests"); above 20 tests the count says "many tests", and its window lists them only after a click on "Show them". A note shows its own linked tests. Below 720 px of column the notes fold to marks at the right edge, and the pointer on a mark shows the note as a window. The mark of a step stands beside the mark of its function, in its lane, so no two marks lie on top of each other. A file of 1,500 lines with 150 notes places its cards in about 3 ms.
- **A notebook** (`.ipynb`) shows as its cells, one under the other, in the file tab, on "Diffs" and in a hover window: a quiet head row for each cell ("cell 3 · code · id fee", "cell 4 · text"), then its lines, numbered inside the cell. A text cell (Markdown) shows its text as written, with no colour of code. An output is not shown; a cell that has one says "output not shown" in its head. The head says what the change did to a cell: "new", "removed", "changed", "moved from cell 6", "moved to cell 2"; a changed cell has one head over its removed and its added rows. The rows count in the text of the cells (`shared/notebook.ts`), so the notes, the places of a diagram, the join both ways, the marks, Alt+Down and Alt+Up and the drawing of only the rows in view work as for any file (`cellRows()` in `code-notes.js`, from `cells` of the page file or of the answer to `code:<path>`). A notebook in which only outputs or run counts changed is one folded row, "only outputs changed"; a `.ipynb` file that does not read as a notebook shows as text, with "does not read as a notebook, shown as text" beside its name.
- **A note on removed lines** (`"removed": true`) looks and works like any note: its card stands at the height of its first removed row, joined to the middle of its removed rows. A file that the change deleted shows all its lines as removed rows, with its notes beside them; it stays on the change page, since VS Code has no file to open as a tab.
- **One part of the code for "code with notes"**: `codeWithNotes()` in `code-notes.js` draws the rows, wraps them, places the notes and lights them. The file tab, each file of "Diffs" and the hover windows of a diff, of code lines and of tests all use it. A row of a removed line counts in the file as it was; every other row in the file now (`spanOf`).
- **A very long line** that takes more than 8 visual rows shows its first 8 rows and "Show all 30,000 characters"; the click shows all of it.
- **A file with no text to show** says what it is in one line: "Binary file, 4 KB", "Empty file", "Link to src/app.py", "Only the mode changed: now executable". A picture shows as a picture; a changed picture shows before and after side by side. The same holds in a file tab, on "Diffs" and in the hover window of the file. `page-data.ts` finds these facts once for each page (`describeFiles`), and sends a picture only when the page asks (`picture:<path>`).
- **A renamed file** is one file with "renamed from <old path>", and only its changed lines are marked. A part that names the old path lists it once, under the new name; the summary line says "1 file named by the old path".
- **The colour of a note**: a note has the colour of its code. Beside added lines its card, its join line and its narrow mark are green as the added rows; beside removed lines they are red as the removed rows; a note on lines that the change left alone is plain (`toneOf()` in `code-notes.js`).
- **The notes of other changes**: the file tab also shows the notes of every other described change of the repo whose lines are still the same, by the rule of `shared/notes-beside-code.ts` (they come with the answer to `code:<path>`, `notesBeside()` in `page-data.ts`). Such a note has no colour of added or removed lines, and its card says "From “<the title of its change>”". The notes of the map come the same way; their card is the title and the text alone, since a note of the map is about the code as it is now. The hover in the editor still says where a note came from. A comment on it is a comment on its lines. When the branch has no stored change, the file tab shows the code as it is, with no diff and no control of the diffs, and these notes beside it (`filePage()`).
- **Where a file opens**: at the lines that were asked for; else at its first change, when that change is below the first screen (a file of 2,400 lines with one change at the end does not open at line 1); else at its top.
- **Going through the diffs**: a quiet control at the top right says "file 4 of 47" with ‹ and ›, and "change 3 of 12" with ↑ and ↓. J and K open the next and the previous changed file; Alt+Down and Alt+Up go from change to change by the rule of a step of "Diffs" (`fileSteps()`): the reading line a third down, the glide, the two rows that stay. Rows of a whole file between two changes that would fill a view with no changed row are passed: the next change comes to the reading line. After the last change of a file a key opens the next file, at its first change (Alt+Up: the file before, at its last change). The counter is the counter of "Diffs", counted in the file: at its top it names the first change, the one below the reading line. The file beside the diagram of a part steps through its changes by the same rule and stops after its last change, since the next file would leave the diagram. A jump to the lines of a note or a comment is no step: those lines come three rows below the top. The next file opens in the same tab, in the order of the parts, the files in no part last, the generated files left out. A click on "file 4 of 47" lists every changed file under the names of the parts, with its counts.

## The comments window

- **A window of its own** at the right edge of the page and of each file tab, over the full height. Beside code with notes it takes no room of its own: it lies over the notes column, below the control of the files, so the code keeps its width; in a file tab with notes it starts folded, until he opens it. It is hidden when there is no comment and no open point. "›" folds it to a rail with the number of open threads and points. Below 900 px it starts folded and opens over the page.
- **Two categories**, each with its count and its own fold: "Comments", one card for each open thread (its place, the comments and answers, the state line, "Reply", "Resolve"; "N resolved" with "Reopen"), and "Open points", the findings of the fresh check. A click on a card shows its place; a reply on an open point starts a thread tied to it.
- **Writing**: Cmd+Shift+. turns the pointer into a comment icon; Esc, or the key again, turns it back, and no hover window opens meanwhile. The next click sticks a small box at that place, on the thing or code line under it (lines selected before the key stay the target). A click outside an empty box removes it; with text in it, "Discard this comment?" asks first, with "Discard" and "Keep writing". Enter saves, and the box moves into the window in a quarter of a second (no movement with reduced motion); Shift+Enter makes a new line; Esc closes.
- **The quick comment**: Enter after Cmd+Shift+., with no click, sticks the box on the whole of what the page shows: the file of a file tab, the diagram in view, or the diagram of the change (`wholeView` in `remarks.js`). With lines selected, it sticks on those lines. For a comment on a whole file the agent also gets the notes of the file with their lines and the diagrams that the file is in (`aboutInChange` in `shared/context.ts`).
- **A comment on any component**: under the comment pointer, the smallest thing under it has a quiet outline, and a click sticks the box on it: a part; a file name inside a part (it wins over the part); "5 more files"; the box "In no part"; a node of any diagram, with or without code lines; an arrow with its label; a participant and a message of a sequence diagram; a state and a transition of a state diagram; the diagram as a whole, on its title row or an empty place of its surface (a part wins over the diagram); on "Diffs" the head of a file and a line in the file now; in a file tab and in a hover window a code line, a note and a test (a hover window that the pointer is in stays when the key is pressed). The box names the thing in plain words, as `Arrow "API" to "Service"`. The same holds in the large view of a part's diagram and of a wider diagram, and in a part's diagram kept whole after drill up. `media/places.js` makes every target and says where it is: each drawing marks its things with `Places.mark()` (the target in `data-remark`, a key in `data-rk`), with the ids of the Mermaid text that `page-data.ts` reads with `diagramGraph()`.
- **A click on a card** (in a file tab too, where the change page then shows and lights the thing) goes to the view that shows its thing (the change, the large view of a part's or a wider diagram, "Diffs", the tab of the file), moves the surface to it and lights it for 1.6 seconds, as code lines are lit; the pointer on a card lights it quietly. A thing with an open thread has the small circle with the count (on a drawn box at its top right corner). A thing that the change file no longer holds says "no longer in the diagram" on its card, and its click goes to its part, else its diagram.
- **The session of a thread**: a running or answered thread has the link "session". It opens the session in its app when the app has a link of its own (`sessionLink()`), else a terminal of VS Code in the folder of the change that continues it (`openSessionCommand()`: `claude --resume <id>`, `codex resume <id>`). A run that Apostil starts keeps the session that it reports (`setRunSession()`). An agent can resolve a thread with `apostil resolve <id>`; "N resolved" then says "resolved by Claude Code".
- **What the agent gets with a comment** (build 66): the thing (its title, kind, file and lines, a step's note), and for a thing of a diagram the diagram as text, one line for each box and each arrow, at most 80 lines and one line for those left out (`diagramText()` in `shared/comment-lines.ts`; a drawn process of Home is made from the map by `mapDrawing()`, because its step ids such as `s21` change when the map is written again). A comment keeps the title, diagram, file and lines of its thing (`kept` in its target, saved by `withKept()`); when the thing is gone or names another thing, the agent gets one line that says the map was written again and what the comment was put on, and the card shows the kept title.
- **Rights of a comment run**: a Claude Code run that a comment starts has `Read`, `Grep`, `Glob`, `Edit`, `Write` and `Bash(apostil *)`. The setting `apostil.commentRuns` ("read and edit", the default, or "read only": no `Edit`, `Write` or `NotebookEdit`) sets it. Codex keeps its sandbox. The files that the run changed come from Git before and after (`workingFiles()`), are kept on the remark (`changed`) and show as one quiet line under its answer, each a link that opens the file.
- **A line from a card to its thing**: the pointer on a card draws a thin curve to its node, arrow, part, file row or code line in view, with a dot at the thing (`lineFrom()` in `remarks.js`, class `remark-line`); a thing that is not on the page has no line.
- **`@` sends**: typing `@` lists whom a comment can go to: `claude-current` (the session that made the change, named when its name is known) first, then `<app>-new` for each agent app on the path. Letters cut the list; the grey rest of the lit name follows the cursor; Up and Down move; Tab or Enter writes the name as one unit. A comment with a mention is sent when it is saved; one without stays open as a note. In VS Code's input box, a typed `@claude-current` or `@codex-new` sends too.
- **A sent comment starts by itself.** One to `<app>-new` starts a new session. One to the session of the change is taken by that session when it listens (its hook); when it does not listen, Apostil continues that session with the comment at once, with no click. Only a session that cannot be continued waits, and its line says how to reach it. "Start a run" stays as the way for a comment that was sent from outside the page.
- **When a run gives no answer**, the comment is open again and VS Code shows why in one line, with what the program said: for example that Codex refuses the model of its settings. For that case the line has a button that opens the setting `apostil.codexModel`: the model for the Codex runs that Apostil starts. Empty, Codex takes the model of its own settings. A Codex run may write in the folder of the change and in the folder of Apostil's store, where its answer goes, and nowhere else.
- **`@github`**: when the change has an open pull request, the box on code lines offers one more choice, `@github`, "a comment on pull request #12", and one quiet line in the box says that it exists. With it, Enter posts the comment on those lines of the pull request: an added or unchanged line on the side of the file as it is now, a removed line on the side of the file as it was, a selection of lines as a range. It works in a file tab, on the "Diffs" page and in a hover window of code. GitHub takes a comment only on a line of its diff, and the line numbers are right only when the code here is the head commit of the pull request (`pullLines()` in `page-data.ts` reads the diff from the merge base, as GitHub shows it). So the choice is not offered on a line outside the diff, in a file with changes that are not committed, or when the branch here is not at the head commit ("The branch here is not at the commit of the pull request. Pull or push first."), and the quiet line says why. With his review that is not sent yet, GitHub puts the comment into it, and the box says so before he sends. A page of a pull request with no stored change offers `@github` only. The file tabs learn the pull request from the page that read it.

## The checks: `npm run check`, under 2 minutes

`npm run check` runs every check, and it must finish in under 2 minutes on the owner's Mac: it fails by itself when the total passes 2 minutes, so a later build cannot slow it down without noticing. Keep the checks few (one check for one behaviour, at the cheapest level: a unit test for logic, a browser check for drawing, pointer and keys, the window run only for what needs VS Code itself) and wait for a state, never for a fixed time.

It takes the window lock first (one check window at a time on a Mac: the folder `apostil-vscode-window.lock` in the temporary folder, or the one that `APOSTIL_WINDOW_LOCK` names; a lock older than 30 minutes with no check window is taken away), builds once, and then runs at the same time:

| Part | What it checks | Needs |
|---|---|---|
| unit tests | `node --test "out/**/*.test.js"`: the logic, the store, the command line (called inside the test program; three tests start the real program, for standard input, the inbox hook and writers at the same time). | Node |
| browser groups | `view/browser/<group>.mjs`, each a program with its own headless browser: the pages of `view/media` as files, with the drawing, the pointer, the keys and the themes. | Playwright |
| window | `view/window-check.mjs`: one start of a real VS Code window, one part after the other (below). | Playwright, VS Code |
| package check | `out/view/package-check.js`, after the window: the `.vsix` of this build, installed into a VS Code of its own with a home folder and a path of its own. | VS Code |

The unit tests and the browser groups run with a lower priority (`nice`), because a busy Mac slows the real window most. The run prints the count and the time of each part and the total, and keeps all that each part printed in `apostil-check/` in the temporary folder. `npm run check -- --pictures [<folder>]` takes the pictures that a person looks at, at double size; a failed check always takes one (`failed-<group>-<n>.png`). `APOSTIL_TIMES=1` shows when each check of the window run ended.

A part alone: `npm test`; `node view/browser-check.mjs [--group <name>] [--pictures] [<folder>]`, or one group with `node view/browser/<group>.mjs`; `node view/window-check.mjs` (take the window lock yourself); `npm run package && npm run check-package`. Build first.

**A real pull request in a browser**, read only, for a look with your own eyes:

```bash
npm run build
node out/view/pull-request-data.js https://github.com/owner/repo/pull/12 26h
```

The second argument is when he last looked: hours back (`26h`), a time, or `never`. The third is the file name next to `page.html` (default `pull-data-12.js`, the name that a click on another pull request of a stack opens; `pull-data*.js` is not in Git). The command prints the address to open in a browser: `file://<this folder>/view/media/page.html?pull=pull-data-12.js`.

**The settings of the check windows.** Every window that a check starts gets `CHECK_SETTINGS` of `shared/run-in-vscode.ts`: `apostil.homeWhenEmpty` is off. `runInVsCode()` writes them; `view/window-check.mjs` turns the setting on for its first part and off again.
