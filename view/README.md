# The view

A VS Code extension: the list of changes in the sidebar, one page that shows a change as a diagram or as all its diffs, and a tab for each of its files with the whole file and its notes. The page fills its tab and uses the fonts and sizes of VS Code.

## Run it against a repo

```bash
npm ci && npm run build
code --extensionDevelopmentPath="$PWD" /path/to/a/repo
```

Install with `npm ci`, which takes exactly the versions of `package-lock.json`. The file `.npmrc` turns install scripts off (`ignore-scripts=true`), so no package runs code when it is installed. `npm run package` makes the `.vsix` with `vsce`, a dev dependency with an exact version, so its packages are in the lockfile too and `npm audit` and Dependabot see them.

Open "Apostil" in the activity bar and click a change. Cmd+Shift+. on the page or in a file tab turns the pointer into a comment icon, and the next click opens a comment card there; on lines selected in an editor it asks in VS Code's input box. Set `APOSTIL_HOME` to read another store than `~/.apostil`. The code says "remark"; the page says "comment".

## The list

- **The list** puts the changes of one agent session under one head: the icon of the app and the name of the session as its link ("session" when no name is known), on one line, cut with dots when it is too long, with the full name in the tooltip. The `@` list cuts a long session name the same way. The name comes from the app's own files (`sessionName()` in `shared/agents.ts`), else from `apostil save --session-name`. Under a row, its pull requests (the icon of the state, then `#12 review needed`), loaded after the list is drawn and kept for 60 seconds; more than two in a session fold. A pull request in a stack has a quiet mark of its place ("2/3"), and its tooltip adds it ("#14 · Review needed · 2 of 3 in a stack"). Rows of one session whose pull requests are in one stack stand together, in the order of the stack, the top first. A click on one opens the page of its change at "Conversation". Each row has one state line: the agent is working, answers to read, remarks waiting, or what the row said before.
- **People on a pull request line.** The avatar of its author stands at its left, and its reviewers stand small at its right end, lying over each other, each with a dot in the colour of its state: three show, then a count ("+1") as one more face of the same size, a light grey disc that lies behind the third face, in the order of the status strip of the page (`reviewerFaces()` in `media/tools.js`, which the strip uses too). A person with no picture is a round mark with the first letter of the login; a known product has its icon. The state words are cut with dots when the line is too short, so the row keeps its lines.
- **The search.** The search is one icon at the right end of the row "Home". A click shows the field under the row with the keyboard in it; a click on the icon while the field shows hides it and ends its search (a sort or filter stays, and the icon stays marked while one is on); Escape in the empty field hides it too, and so does a click elsewhere that takes the keyboard from it; after the click of that press, so the rows do not move up under the pointer and the click is not lost. The icon takes no keyboard on a press, so the field does not close and open again. The field, "Search changes", with a clear mark and the icon "Sort and filter" at its right end. Typing filters the rows at once: a row stays when its branch, its agent app, or the number, title, author, a reviewer or a label of one of its pull requests holds each word of the text (no case). Filters are words in the field, as on GitHub: `author:<login>`, `reviewer:<login>`, `label:<name>`, `state:<state word>` (also `state:"no pull request"`), `agent:<app>` (`agent:claude`); a name with a space is quoted, an unknown word is plain text, and words of one key are "or", keys "and". One parser reads the field (`parse()` in `media/search.js`). Escape in the field empties it. The icon (a click, Enter on it, or Down in the field) and the command "Apostil: Sort and Filter the Changes" open "Sort and filter", **VS Code's own quick pick** at the top of the window (a view of the side bar is its own frame and can draw only inside it, so a menu in the view could not stand in front of "Files"). The view counts the values (`menuValues()` in `media/search.js`) and sends them with the search (message `menu`); `sort-filter.ts` makes the lines (the groups Sort, Author, Reviewer, Label, State and Agent, each with only the values that the rows have, their count in the description) and `sort-filter-pick.ts` shows them: an author and a reviewer have their avatar, a label a dot in its colour, a state a codicon in a colour of the theme, an agent the icon of its app. Each line has a check box; a click or Space on a line is one pick, and a pick writes its word into the field or takes it away (the sort that is on turns its order round, another sort replaces it). The list changes at once (VS Code sends the new search back to the view, message `search`, and keeps it), and the quick pick stays open with the line under the keyboard. Typing in it narrows the lines. Escape or a click outside closes it; so do Enter and "OK". The box "select all", the count of the checked lines and the button "OK" are VS Code's, and its API cannot hide them; "select all" does nothing. The sorts: modified (the default, newest first), created (newest first), author (A to Z) and size (lines added and removed, the largest first); a second click on the sort that is on turns it round. Modified is the latest of the last save of the change and the last update of its pull requests; created is the first save of the change when the store has it, else the creation of its oldest pull request, else the first commit of the branch (its author date). While a sort other than modified, newest first, or a filter word is on, the icon has a small dot.
- **The list while a search is on.** With an empty field and the default sort, the list stands by session, as above. With text, a filter or another sort it is one flat list of the rows that match, in the order of the sort, with no heads of sessions and no folds of rows ("History" rows match too); each row has the icon of its agent app before its branch. The line under the field says "3 of 12 changes", or "No change matches · Clear". A filter on pull requests shows only the pull requests of a row that fit it, and text that only some pull requests hold shows only those; text that the branch or the app holds shows the row as it is.
- **What is kept.** The text of the field and the sort stay when the list is drawn again and when the view is hidden and shown: the page sends each change to VS Code, which keeps it in the state of the workspace for each repo (`apostil.listSearch:<repo id>`), so it stays after a restart, and sends it back with the rows. What is unfolded is not kept.
- **Its data.** `gh pr list` gives the author, the labels with their colours, the reviewers asked (`reviewRequests`) and the newest review of each reviewer (`latestReviews`), and the dates of creation and update, all in one call. `pullRequestsFromJson()` in `shared/pull-requests.ts` maps them in one place, with `person()` and `reviewersOf()` of `shared/pull-request-facts.ts`, which the page of a pull request uses too. The list of gh gives no address of a picture: a person gets `https://avatars.githubusercontent.com/<login>?s=40` (a stand-in `gh` of a check can give `avatarUrl`); a bot and a team get none. `list.html` allows pictures from the same hosts as `page.html`. A row sends its dates as ISO values beside its age: `savedAt`, `firstSavedAt` and `firstCommitAt`. With no `gh` or no GitHub remote the search and the sort work on what the rows have (branch, agent, dates, sizes), and the quick pick leaves out the sort by author and the filters author, reviewer and label.

- **Open pull requests with no stored change**. Under the rows stands the quiet head "Pull requests", with the count of all the open pull requests of the repo beside it, the same number as the badge of the Apostil icon (`pullCount()` in `media/list.js`, "21 open pull requests in this repo" on the pointer), and one row for each open pull request of the repo whose branch has no row: its title, then its line (number, state, people). At most 20 show, then "n more" opens the rest. `readRepoPulls()` in `shared/repo-pulls.ts` asks `gh pr list --state open --limit 100` once (`repoPullsLater()` keeps the answer 60 seconds and adds the places in stacks); the view gets it as the message `repoPulls` after the rows. The search, the sort, the filters and the order of a look read these rows as any row (`pullAsRow()` in `list.js`). A click opens its page (`openRepoPull`, by its link, as "Apostil: Open pull request…"). When gh is missing, is not signed in, has no remote or fails, one quiet line under the head says why (`ghProblem()`: "gh is not signed in: run gh auth login"). The call runs on the side of the extension (`extensionKind` is `workspace`): in a remote window or a codespace that is the other computer, with its own gh and sign-in. The page of such a pull request says in one quiet line that it has no description of Apostil yet, and one direct link, "Describe it with a new Claude Code session", that has an agent session describe it (see "A link that has an agent do it"). A click on the row of the open branch with no change file opens Home when it has no commit and no changed file against its base; with changes it opens the page of the branch (`openBranch()` in `change-page.ts`, `branchPage()` in `page-data.ts`): "Diffs" with every changed file against its base, committed or not, all in no part, no diagram, and the line "This branch has no description of Apostil yet." with the press that has an agent describe it (`BRANCH_WORDS` of `shared/ask.ts`, the same run as for a pull request). When the branch gets its change file, the page shows that change.
- **A change that is not checked out**. `changeWhere()` in `shared/change-rows.ts` says where Git is read for a change: its own folder while it is a Git folder, else the open folder; when that folder is not on the branch of the change, the files, counts and diffs come from the commits from its base to the commit that the change was saved at (`changedFiles(folder, base, head)`), on the row, on the page and on the graphs page. The page says "as saved at commit abc1234; this folder is on main" in its summary line. When the clone has no such commit, the row and the page say so in one line and show no counts. A working tree is never counted for it.

## A pull request

- **Where it opens.** The page of a change whose branch has a pull request opens at "Conversation", from every place that opens a change: its switch reads "Conversation · Diagram · Diffs". A change with none opens at "Diagram" ("Diagram · Diffs"). The page must not draw "Diagram" first and switch later, so the extension sends the pull requests of the branch with the page data when `pullRequestsLater()` kept them (`keptPullRequests()` in `change-list.ts`, in `dataFor()`); the page then chooses its first view at once (`firstView()` in `page.js`; the base order of `change-view` in `marks.js` puts "Conversation" first when `hasPull`). When none are kept, the page waits for the `pulls` message at most 1.5 seconds (`PULLS_WAIT_MS`, `App.waitForPulls()`) with the quiet line "Looking for the pull request of this branch…", then opens at what it knows; an answer that comes later redraws only the switch and the strip. A step that goes to a place (the path back, a link to a part or a diagram, a file tab, `?go=`) opens at that place and ends the wait. A rule of a look that orders the views wins. As a file in a browser, `page.html` shows the pull requests after the first view, as VS Code does when nothing is kept; `?pulls=kept` has them at once and `?pulls=none` is a branch with none. The state of the pull request stands in the status strip under the top line. A branch with more than one pull request shows the newest open one, and "1 more pull request" in the strip opens a small choice. A click on a pull request in the list of the side bar opens the page of its change at "Conversation". In the list each row shows its own open pull requests, two at most; its merged and closed ones are behind the fold of that row. One session shows at most two rows with an open pull request, and one line ("3 more pull requests") shows the others and folds them again ("Show fewer"). The row that is open now and a row with no pull request always show. A row whose pull requests are all merged or closed stands under the line "History · 2" at the end of its session, folded at first (`foldRows` and `foldPulls` in `media/states.js`). "Apostil: Open pull request…" takes a number or a link. A pull request of a branch with a stored change opens that page. Any other gets a page of its own with "Conversation" and "Diffs": its files in no part when its commits are in the folder, else one line with the command that gets them (`git fetch origin pull/12/head`) and its files with their counts from GitHub. A link to another repo gives "Conversation" and "Files". A number that does not exist names the tab "Pull request 999 not found" and offers no view. The line at the top holds the pull request as a step, "Pull request #12".
- **A stack of pull requests.** GitHub merges a stack from the bottom; each pull request targets the branch of the one below it. The stack is read with the pull request: its number, size and base, and for each pull request its place, number, title, state and draft. Its entries are read page by page too (`LIMITS.stack`, 200). Under the title stands "2 of 3 in a stack onto main", and beside the branches the pull request below ("`stacked-on-big → big-feature` · on #2"). The list of the stack has one row for each pull request, the top first: its state icon, number, title on one line, and "this one". In "Messages" it is folded into the line "2 of 3 in a stack onto main", and a click opens it; in "Classic" it is a box above the first comment. A click on another row or on "on #2" opens that pull request in the same tab, as a step of the path, so the line at the top leads back. As a file in a browser it opens `page.html?pull=pull-data-<number>.js`. The merge sentence of a pull request with an open one below it starts with "Waits for #2 below it in the stack"; the lowest one says what it says alone, and "The stack of 3 is ready to merge" when every open pull request of the stack is ready to merge. Joining or leaving a stack is a quiet row. The list of the side bar reads the places of all pull requests of the repo once, from `GET repos/{owner}/{repo}/stacks`. A page of a pull request with no stored change compares with its base, which for a stacked one is the branch below. A stored change of a branch on top of another branch says "compared with big-feature" in its summary line (`baseBranchOf()` in `shared/git.ts`). Creating, changing or merging a stack is not built, nor a diagram of a whole stack.
- **Reading.** `shared/read-pull-request.ts` asks `gh api graphql` (read only, 30 seconds at most for each call) and reads every list page by page; `pullRequestFrom()` turns the raw JSON into one plain object. The timeline is read from its end, so a limit keeps the newest items ("219 earlier items are on GitHub"). The checks are read page by page too. The limits stand in `LIMITS`: 1,000 timeline items, 300 threads, 100 comments in a thread, 3,000 files, 1,000 checks, 50 notes of a check. What a limit cuts off is counted, and the page says so with a link to GitHub; a cut list of checks never says "all passed". A second small query counts how far the branch is behind its base. On HTTP 502 or 504 the read starts again with smaller pages (50, 25, 10). A large pull request shows its head as soon as the first answer is there, with "Reading the conversation: 300 of about 900 items", and fills in the rest.
- **What comes with it** (`shared/pull-request-facts.ts`). Every check run (workflow, job, state, time, log, run page, notes on code lines) and every status of another product; of a job that ran twice only the newest run counts. The newest deployment of each environment. One sentence of what stands between the pull request and a merge, from what GitHub says: "Ready to merge", "Blocked: 2 checks failed · An approving review is needed · 3 commits behind main", "Auto-merge is on: …", "In the merge queue", "Merged by ines on 3 November with a squash", "Closed, not merged"; the hardest first. While GitHub does not know yet ("GitHub is still working it out"), the page asks again after 6 seconds, three times at most. Labels, assignees, reviewers with their states (a team, Copilot), the milestone, the issues that it closes, the tasks of the description. A commit has "Verified" when GitHub verified it, and names its author also with no account. Known products get their name and icon (`PRODUCTS`: GitHub Actions, Dependabot, Copilot); every other bot keeps its login and a quiet "bot" mark. A comment from a person's account stays that person's.
- **The state** follows the facts (`STATES` in `shared/pull-requests.ts`): "ready to merge" only when the review is approved, or in a repo that asks for no review when at least one check ran and all passed, and never while GitHub does not know about conflicts; else "review needed".
- **When it fails**, the page says why in one plain line and offers "Try again": `gh` is not installed, not signed in, no network or no answer in 30 seconds, no such pull request, no GitHub remote for a number, the rate limit (with the time it ends), a request too large for GitHub, an answer that is not what the code expects.
- **What GitHub sends is not trusted.** The HTML of a description or a comment goes into the page only through `cleanHtml()` in `shared/clean-html.ts`: an allow-list of tags and attributes, every text escaped. A link becomes `data-link`, which VS Code opens in the browser. A picture stays only over https from GitHub's hosts. A picture of a private repo is fetched by the extension with the login of `gh` and handed to the page as a data address (`shared/pull-pictures.ts`); the browser command does the same. A picture that does not load is its text and a link. A picture is at most about 360 px high; a click shows it large. A Mermaid block is drawn with the Mermaid of the page and its safe settings, and stays code when it does not parse. Text for screen readers only ("Loading") is left out.
- **The page and the window of the conversation**. The page of a pull request always opens at its top: the strip, the title, the facts line, the state card and the description, also when he opened it before and messages are unseen. It never scrolls by itself to the conversation when it opens; the press "Merge" of the strip still opens it at the card with its merge step. Drawn again for the same pull request (the other look, more of a large read), the page stays where it is. The conversation is a window of its own in the column, under the description (`#cwin`, drawn in `draw()`): its head ("Conversation · 13 messages", "Messages · Classic") at its top, the box to write at its bottom, always in view, and its own scroll between (`#cscroll`). It is as tall as the view less the slim bar (`max-height` in `look.css`), and no taller than what it holds: two messages make a short window. The wheel and touch scroll the window while the pointer is in it; at its top or bottom end the page scrolls on, so nothing traps the pointer. "↓ Newest" belongs to the window: in the middle of its lower edge, just above the box, while the window is not at its newest message; a press keeps the keyboard in the box. A link to a message or a thread brings the window into view and scrolls the window to it (`toInWindow()`: the comments meter and the blocker of the state card go to the first open thread); Cmd+Shift+. brings the window into view with the cursor in its box (`showWindow()`). A comment or a review that he sends stands at the end at once: at the newest message the window keeps the end in view, else "↓ Newest" counts it ("↓ 1 new", `cameAtEnd()`). Items of others still come at the next drawing. There is no link from a mark of a file tab to a message: a thread beside the code is not built.
- **When he last looked.** The store keeps, for each pull request, the time he last opened its conversation (`pull_request_look`). The window of the conversation opens as a chat app opens a conversation: at the oldest thing that he has not seen, at its top edge. "Messages" draws "New since you last looked · 4" above the first newer item; "Classic" opens at its first unseen row from the top, or at a new answer of others in an earlier thread, with no line (GitHub's look has none; `classicNew`, `data-first-unseen`). The time is then set to now, but the page keeps the time from before it opened (`App.since`), so a later read after a write and a way back to "Conversation" open the window at the same place. Never opened before: the window opens at its first message. Nothing new: at its newest message. The middle of a long "Classic" conversation never folds an unseen row. In "Details", the labels open their search on GitHub and "Tasks" opens the description at its tasks, as in the facts line.
- **The status strip** is one short line and says each fact once: the icon of the state (its word only for a draft and for conflicts), the reviewers as avatars that lie over each other, the first one whole and on top, each with a small dot in the colour of its state (the pointer says the name and the state; three show, who asked for changes first and a person before a team and a bot; the others are a count that names each one, as one more face behind the third), the checks ("2 of 12 checks failed"; a click opens their list, which names the failed ones), and the first thing that still stands before a merge with a count of the others ("2 more"; the pointer on it says them all), without what the strip said before it ("1 check is still running · 5 commits behind main"); for a merged or closed pull request only who did it and when. The state card keeps the whole sentence. When he may merge it now, the strip has a quiet "Merge" before "Review", also in "Diagram" and "Diffs": it opens "Conversation" at the card with its merge step open. A click on the checks opens their list under the strip: under the name of their workflow ("CI · GitHub Actions"), other products under "Other checks"; failed first, then waiting and running, the passed ones as one folded row ("7 passed"), skipped ones quiet. A failed check shows its notes with `file:line` (a click opens the file tab at that line), "View the log" and "Run again" (links to GitHub). The deployments stand there too ("preview: ready · staging: failed").
- **"Messages" is the modern look, a calm chat on a timeline**: oldest first, the newest last, next to the box. A thin line (a hairline in `--line`) runs down the avatar column of the feed, under everything (`.feed::before`, `z-index:-1` in the feed): an avatar has a ring in the colour of the window, so the line stops short of it; the day lines, "New since you last looked", the fold of earlier messages, a thread, a review card and his own messages stand over it. A message of others stands at the left: the avatar, then the name, then the text. The time has one place: the first message of a group has one relative time in its name line after a middle dot, in faint text ("mira-k · 19 h ago", `timeAgo()`; the dot is drawn by `look.css`), with the exact date and time in its tooltip; the date stands in the day lines ("Today", "Yesterday", "3 November", centred quiet lines). Messages of one person in a row, within 5 minutes, are one group (`sameAuthor()`): one avatar, one name and one time at the start, then the messages close together with no time, their exact time in their tooltip. In a thread the same holds; its first comment has no time either, since the message around the thread says it. His own messages (`mine`) stand at the right in a bubble tinted with `--tealsoft`, with no avatar, their relative time above the bubble at the start of a group; his name is there for a screen reader only (`ownName()`, class `sr`); his own review stands at the right too, as its card. A heading at the start of a message is its title line. A review is a soft card with its verdict and icon, its threads under it. **Rows on the line** (`lineRow()`): commits, events and the comments of a product are rows with their small icon on the line and a short faint word beside it, with no box, no border and no time: "4 commits", "3 force pushes", "2 deployments", "label backend", "review asked from lena-s", "merged" (`LINE_WORDS` and `lineWords()`); a run of events is one row for each kind, in the order of their first event. A product is one row with its icon: "GitHub Actions · 2 comments". A click on a row opens its details in place: the commits with their short hashes, the events with their whole words, the comments of the product with their title lines and texts; each detail row has its exact time in its tooltip. Equal messages of one author are one, "posted 3 times" (all their times in its tooltip). Reactions are small chips. The side facts are one quiet line under the title with "Details". More than 4 messages before the line fold into one row at the top of the window, drawn when he opens it, in place: the earlier messages stand where the fold stood and the window does not jump (`unfoldInPlace()`). A slim bar with the state icon and the title stays at the top of the page once the title is scrolled away. Nothing moves by itself: no animation of messages, no typing dots.
- **"Classic" is the look of GitHub's conversation tab**, in the same window: the stack and the description are the first boxes of GitHub's line above the window (`classicTopHtml()`), so that the page opens with them, and the window holds the rest of the line. A line down the left side, a box for each comment with a head bar ("ines commented 3 days ago", marks "Author", "Owner", "bot", "edited"), events as small rows with their icon on the line (a commit with "Verified" and its short hash at the right, a label with its pill), a review as a row with its verdict and its threads as boxes, resolved and outdated threads folded with "Show resolved" and "Show outdated". The time always follows the words. More than 60 rows hide their middle behind "Show N more". Its state is the state card at the top, as in "Messages"; there is no merge box at the end. At 1000 px and wider the side facts are a column at the right (Reviewers, Assignees, Labels, Milestone, Closes, Tasks); narrower, they stand under the title.
- **Threads**: a thread is one compact card in the flow; it shows its file and lines ("whole file", "file removed"), its last 6 lines of code, its comments and its answer field. In "Messages" its comments read as a small chat: his own answer at the right in a tinted bubble, and a comment right after one of the same person within minutes with no avatar, no name and no time (its exact time in its tooltip). A long code line wraps and goes on at its indent plus 2 characters: nothing is cut off. The folded code lines are drawn only when he opens them.
- **The look on a dark theme** of VS Code: `look.css` has dark values of its colours under `body.vscode-dark`; labels take their own colour in a readable mix.
- **A long conversation**: the earlier messages are drawn only when he opens them. Every row of the window is laid out (1,500 rows take about 0.2 s): with `content-visibility: auto`, a window below the view would guess heights and open at a wrong place.
- **The icon of a state** stands before every pull request: the list of the side bar, the status strip, the choice, the slim bar. `STATE_LOOKS` in `shared/pull-requests.ts` maps each state to its icon in `media/icons/` and its colour, beside the state words. When the pointer rests on an icon, or the icon has the keyboard focus, a small dark tooltip says "#12 · Review needed", in a stack "#14 · Review needed · 2 of 3 in a stack" (`Tip` in `media/tools.js`). The icon files stay as they are: `state-icons.ts` turns each into a data address for a CSS mask (`.pri` for the state, `.ico` for the others), so an icon takes its colour through `currentColor`.
- **Writing to GitHub** (`shared/write-pull-request.ts`). Nothing goes to GitHub unless the owner sends it himself, with a button or with Cmd+Enter in a field. No write happens when the page loads or a tab closes, and a failed send is never sent again by the code. Each kind of write is one GraphQL mutation through `gh api graphql --input -` ("Commit suggestion" is a read of each file, one commit and a resolve of each thread): the query and its variables go to `gh` as JSON on standard input, so no text of a comment is on the command line. Each mutation asks for what it made (the comment, the review, the thread after a resolve, the commit), and the write answers with it, cleaned as a read is (`commentFrom()` of the reader). The reader learns what a write needs: the node id of the pull request and of each thread, whether he may answer, resolve and unresolve each thread, the lock, whether he opened it himself, his review that is not sent yet with the count of its comments, who gh is signed in as (`viewer`), which comments are his own (`viewerDidAuthor`, `mine`), and whether he may apply a suggestion (`viewerCanApplySuggestion`, `canApply`) with the branch and its repo (`headRepo`, a fork has its own), the merge queue and the side of each thread.
- **An answer in a thread**: in "Messages" and in "Classic" each review thread ends with a quiet field "Answer…". A click or Tab opens it to a few lines with the button "Answer" (Cmd+Enter). A thread that he may resolve has "Resolve" beside it; a resolved one has "Unresolve". As on GitHub, an answer stands only in its thread, as its last message: his own answer is never a row at the end of "Messages" (the reader lists it as a later answer, since GitHub makes a review of its own for each answer), and his own words never count as "New since you last looked" (`mineEntry()`). "Resolve" folds the thread into its one row ("resolved by …"), as on GitHub; "Unresolve" opens it.
- **A suggested change** (a block "```suggestion" in a comment on code): GitHub's own box of it in the HTML becomes one empty mark (`<div data-suggestion>` in `cleanHtml()`), and the page draws the change there from the markdown of the comment (`suggestionsOf()` in the reader): the lines of the thread as they are, removed, and the suggested lines, added. When he may push to the branch it has "Commit suggestion" and "Add suggestion to batch"; in the batch they read "Commit suggestions (2)" and "Remove from batch", and while a batch is open the others only add to it. "Commit suggestion" reads each file at the head of the pull request, checks that the lines are still those of the suggestion, puts the suggested lines in and commits them to the branch in one commit (`createCommitOnBranch`, only while the branch is still at the head that the page read), with GitHub's message ("Update <file>" for one, "Apply suggestions from code review" for a batch) and a "Co-authored-by" line for each author of a suggestion; then it resolves each thread, as GitHub does. The thread folds at once as "suggestion applied by …", and its box then says "Committed as abc1234. Pull to have it here." When GitHub would not apply it, its box says why in GitHub's own words (closed, in the merge queue, outdated, resolved, on removed lines, in a review not sent yet, no change, two on one line in a batch); with no right to push, or more than one suggestion in a comment, it has no button.
- **A comment on the pull request**: the bottom of the window of the conversation is a field "Write a comment…" with the button "Comment". The link to GitHub stays beside the title. Cmd+Shift+. in "Conversation" turns the pointer into the comment icon, as on every view, and a click on a message (a comment, a review, a message in a thread on code) opens the comment card there. Its target is a `message`: the number of the pull request, the id and link of the message, its author and its words in one short line (`paintMessages()` in `remarks.js` marks each `[data-msg]` of `conversation.js`), so that an agent gets the message as context (`aboutTarget()` in `shared/context.ts`). The mark of its threads stands at the end of the name line, after the relative time. In the picker, "The pull request on GitHub" does what `@github` does for that place: an answer in its thread on GitHub for a message in a thread on code, else a comment that quotes the message (`messageChoice()` and `sendOnMessage()` in `conversation.js`).
- **The review**: the strip of an open pull request has a quiet button "Review". It opens a panel under the strip: the text, the three verdicts "Comment", "Approve" and "Request changes", and "Send review". On his own pull request GitHub takes only a comment, so the panel shows no verdict, only one quiet line ("This is your pull request: GitHub lets you comment on it, not approve it or ask for changes."), the text and "Send review", which sends a review that comments. When he has a review that is not sent yet, the strip says "Your review is not sent: 2 comments", and the panel sends that review with its comments. A merged or closed pull request has no "Review". A locked conversation has no field, and one line says that it is locked.
- **A review that is not sent yet**: GitHub puts every new comment on code and every answer in a thread into it, where nobody else sees them until the review is sent. So the box on code and the answer field of a thread both say "This goes into your review that is not sent yet.", the strip says "Your review is not sent: 2 comments", and "Review" sends it with all its comments. (Seen with real sends: an answer in a thread did go into the review.)
- **The state card** (`media/merge-card.js` says what it holds, `conversation.js` draws it): at the top of "Conversation", under the facts line and above the description, in "Messages" and in "Classic". One headline with the icon and colour of the state and one sentence: "Ready to merge", "Able to merge" (with what does not block, as "1 check failed. This does not block a merge."), "Blocked" (what blocks, each a link to its fix: the pull request below in the stack, the list of checks, the review panel, the first thread that is not resolved, which folds open, "Update branch", or GitHub), "Behind", "Conflicts", "Draft", "In the merge queue", "Checking if it can merge", "Merging…", "Merged" (by whom, when, as which commit) and "Closed". What blocks follows GitHub's own word (`mergeStateStatus`): CLEAN, UNSTABLE and HAS_HOOKS can merge, so the rest are notes; BEHIND blocks only for being behind; open threads block when the base asks for it. Three meters, each a link: the checks by state (opens their list under the strip), the threads that are not resolved of all (goes to the first one), and the approvals of those asked or needed (opens the review panel); each has a thin bar, striped when nobody approved. Then the actions: "Merge" is the only filled button of the page, and only when he may merge it now; every other action is a quiet link ("Merge as admin", "Update branch", "Ready for review", "Convert to draft", "Resolve the conflicts on GitHub", "Close pull request", "Reopen", "Delete branch"). The card is the same with and without a look.
- **Who may do what** comes from GitHub's fields, never a guess: `viewerPermission` (WRITE, MAINTAIN or ADMIN may merge), the methods that the repo allows (`mergeCommitAllowed`, `squashMergeAllowed`, `rebaseMergeAllowed`; no merge commit when the base asks for a straight history), `viewerDefaultMergeMethod`, `viewerCanMergeAsAdmin`, `viewerCanUpdate`, `viewerCanClose`, `viewerCanReopen`, `viewerCanUpdateBranch`, `viewerCanDeleteHeadRef` (and no "Delete branch" for a fork or when the repo deletes it by itself, `deleteBranchOnMerge`), the commit title and message that GitHub fills (`viewerMergeHeadlineText`, `viewerMergeBodyText`) and the rule of the base (`refUpdateRule`: approvals needed, threads resolved, straight history). An answer stored with none of these fields offers no action.
- **A merge**: "Merge" opens one step in the card, no modal: the methods of the repo, starting with the one he used last in this repo (kept by the page), else GitHub's for him, each with one sentence; the commit title and message as GitHub fills them, which he may change for a merge commit and a squash (a rebase has none); "Confirm merge" and "Cancel" (Escape). A merge cannot be undone, so the page does not show it before GitHub answers: the card says "Merging…", then the merged state in place, or the step again with his choices and GitHub's reason in one line. The write is `mergePullRequest` with `expectedHeadOid`, so GitHub refuses it when the branch moved since the page read it.
- **Close, reopen, ready for review, convert to draft, update the branch, delete the branch**: each can be undone on GitHub, so it shows at once in the card, the strip and the slim bar, marked "sending", and GitHub answers in the background; a failure puts the pull request back as it was and says GitHub's reason in one line of the card. One mutation each: `closePullRequest`, `reopenPullRequest`, `markPullRequestReadyForReview`, `convertPullRequestToDraft`, `updatePullRequestBranch` (with `expectedHeadOid`; the page keeps the new head) and `deleteRef`.
- **Around a send: at once, then in the background.** The page shows the result of a write at once and the call to GitHub runs in the background (`inBackground()` in `conversation.js`): an answer stands in its thread and a comment or a review at the end, each with the quiet mark "sending"; a resolved thread folds, an unresolved one opens ("Sending…" in place of "Resolve" while it runs). The field is empty and ready for the next words at once. Only that one thread is drawn again in its place (`redrawThread()`): the scroll place stays, every other thread and fold keeps its state (the earlier messages, a long message, a hidden comment, the code lines of a thread), the keyboard focus stays in the field or on "Review", and the field is moved into view only when a new message above it pushed it out of the view or out of what the window shows. When GitHub answers, its comment takes the place of the one that showed, without the mark. When it fails (no network, no right, a lock, a line that GitHub does not take), the page puts the thing back as it was (the answer leaves its thread, a resolved thread opens again, the review panel opens again), his words go back into the field, and GitHub's own sentence stands as one quiet line in that thread or under that field. After a write that went through, the page reads the pull request again in the background (`App.reread()`) and changes only what differs (`Conversation.refresh()`): the strip, each thread whose comments or state changed, the state card; a read that fails changes nothing, and a read while another write ran is not used. Items of others that came meanwhile show at the next drawing of the conversation. The same holds while GitHub works out if it can merge (three reads, 6 seconds apart), and when the pull requests of the branch come again with the same pull request. A text that is not sent yet survives a redraw and a change of the view in the same window; leaving a field asks nothing.
- **In the example** (`page.html` as a file, and `?pull=`), a send goes nowhere: the example answers as GitHub does (`exampleWrite()`: the comment it made, marked "example", the thread after a resolve, a made-up commit), and the page shows it as in VS Code. The browser check makes one send fail with `window.apostilExampleFailure`, and holds the answer with `window.apostilExampleHold` until `window.apostilExampleRelease()`, to see the page while it waits.
- **Not built**: "Viewed" on a file, editing, hiding or deleting a comment, quote reply, reactions, asking for a review again, labels, assignees, editing the title or the description, auto-merge, the merge queue, revert, restore a deleted branch, run a check again (each is a link to GitHub), a thread beside the code in "Diffs" and in a file tab, Option+Right and Option+Left, a list of all pull requests of the repo.

## Links from outside

- **The handler** (`view/link-handler.ts`): `vscode://apostil.apostil/pull?repo=<owner>/<name>&number=<n>` (or `&branch=<branch>`) opens the pull request as "Apostil: Open pull request…" does; for a branch, its pull request asked of GitHub as the list asks, but in the repo of the link (`gh pr list --repo`), so that a clone of a fork finds it. `/change?repo=<owner>/<name>&branch=<branch>` opens the change of that branch, or Home and one line that it has no description yet. The repo is the open folder whose remote on GitHub is `owner/name`, also a remote other than origin; with none, one line offers to open a folder. A link only opens views.
- **The fields** (`shared/apostil-link.ts`): `repo`, `number` and `branch`, each checked (a branch as Git allows it, without `&`). A field it does not know is passed over, such as `url`, which `https://vscode.dev/redirect?url=…` adds on its way; so no field is named `url`. A link never holds a path of the computer.
- **The https form.** GitHub drops a `vscode://` link from its markdown, so every link outside VS Code is the vscode.dev redirect. `apostil link --pr [<number>]`, `apostil link --change` and `--markdown` print it (`store/link-command.ts`); `ICON_URL` is the address of Apostil's icon in the public repo, and the `--markdown` line starts with it. VS Code asks once whether Apostil may open links.
- **Source Control** has Apostil's icon in its title (Git only): it opens the change of the branch, as `/change` does.
- **The switch**: `apostil links off|on|status`, the commands "Apostil: Turn off links and nudges" and "… on", or `APOSTIL_NO_LINKS=1`. It is the file `links-off` in the store folder. While it is off, `apostil link` prints nothing, `apostil hint` (the hint at the start of a session of Claude Code, for a person who adds its hook; `apostil setup` does not) prints nothing, and the icon of Source Control is gone.

The line stands under the head while the repo has no map, and after the words of the summary line when the map shows (`mapRunHtml()` in `media/tools.js`); nothing in it moves, and it goes when the run is done.
  - *The plan of the work*. When a run starts (the press of Home, or the first save of a run that a person started in a chat), the record keeps the plan of the work: the code lines of the repo and, for each step, how many units it has left: the overview, the areas with a diagram of their own, the notes groups (`noteGroups()`), their files and their lines, and the lines of the largest group, the groups of processes and of services, the second process round and the fit round (`MapPlan` in `shared/map-estimate.ts`, `workPlan()` in `store/map-run.ts`). What is not known yet comes from the size of the repo (`areasOfSize()`, `topAreasOfSize()`). The plan is made again when the overview is saved, with the real areas, and when the last notes are saved; a run that goes on after one that stopped makes a new plan of the work that is left. Each save keeps its kind, its minute and for notes its files (`saves`, at most 600), so the pace of the run can be measured. Counts only: the record stays small.
  - *The time left*. One function computes it, `timeLeft()` in `shared/map-estimate.ts`: the expected time of the work left, from the plan, times the pace of the run. The work runs in three stages: the overview alone; the writers (areas, notes, processes and their second rounds, services and marks), which run side by side; and the fit round. A stage takes the longer of its longest unit and all its work over the 16 places (`WRITERS_AT_ONCE`), and 2 minutes of the lead: steps that run at the same time count once, not added. The longest unit of the writers is the largest notes group, then a process writer and its second round. The minutes of each unit are in `WAVE_MINUTES` (from real runs of November 2026): notes at 60 lines a minute, a process writer 15, a second round 8, a service writer 10. A plan with no lines of its groups counts 400 for each. The running stage counts the time that it has already run, and keeps at least a tenth of its time. The pace is the time that the done work took, divided by its expected time; it counts more as more is done, so one slow writer early on moves little. `runTimeLeft()` gives it for an open run of the whole map with a plan once its first notes are saved (before that the pace is not measured, so Home shows no time and no bar), as `time` of the line (`minutes`, `share`). VS Code computes it after each save and every 30 seconds, and sends only the time then (message `time`, `HomePages.tick()`); a rise shows only when two computations in a row agree on it, the smaller of the two, and a fall shows at once (`shownTime()`).
  - *Home while it writes*. The time stands at the right end of the head: "About 14 min left" in whole minutes, under a minute "Less than a minute left", never 0 and never a count of seconds (`#runtime`, `showTime()` in `media/home.js`). When it changes, the old words move up and fade out above the new ones, once. The top edge of the frame is the bar of the run: it fills by the expected time of the work done, out of all, so it moves at an even pace (`runBar()`). Before the overview is saved, the frame holds a soft sketch of a map that shimmers slowly, in place of the wordmark, and the line of the run stands under the head (`runFrame()`, `sketchHtml()` in `media/overview.js`). After it, the top map shows in the overview: a node whose area is done looks normal, and the node of an area with work left has a quiet accent edge (`rn-working`). Its card shows a sketch that shimmers, a small turning mark and its own small bar; a card whose area is done shows its diagram or files. `areaWork()` in `store/map-run.ts` gives the areas with work left (`areas` of the line): the record says what is saved, not which writer runs, so every area with work left counts as worked on: nothing of an area waits for another area (its processes and its marks start as soon as its notes are saved). In full screen the top map shows with the bar and the time, and no cards. When the run ends, the bar, the time and the states go. Movement is slow and stops with `prefers-reduced-motion`.
  - *A run that stopped* says so in the same place: "The map run of Claude Code session 1a2b3c4d stopped after overview, 3 of 8 areas", with the press "Map this repo" (no map) or, in the summary line, "Start again" (on the map; the pointer on it names the app) and "Another app". It goes when a new run starts. A run of Home that failed also has its toast, with its fix.
  - *The list "Repo"*: its row "Home" says "writing the map" at its right while a run writes (`homeRowState()`).
- **Processes**: the map can hold the processes of the repo (`apostil add-processes`), whose steps are its notes of files. Home draws them from the data when the map is read (`shared/process-diagrams.ts`, the same `diagramGraph` and the same stage as every diagram of the map); the map stores no Mermaid text for them. A node with no diagram under it (a node of an area diagram, or of the top diagram for an area with no diagram) whose paths hold the first step of processes goes down to them, not to its code: one process opens that process; several open "Processes of <node>", one node for each process with its title and "N steps", joined by its handoffs, and a process of another place that hands to or from them is a quiet box (dashed, quiet words). A process shows its top steps (a step whose lines no other step of the process holds) in one box for each file, with the arrows of the writer, and each library or program that it calls as a quiet round box. A step that holds steps says "N steps" under its title, and a click opens it: its inner steps in the order of the list, the branch arrows dotted with their labels, and a step of another place that an arrow joins as a quiet box. A click on a step with no inner steps opens its file at its first line (`openFile` with `line`; `apostil.openFile` takes the line, so a file with notes opens in the file tab at that line). The pointer on a step shows its note, its file and its lines; on a process, its summary and its count of steps. A step whose note is gone (the notes of its file were written again) is left out of the drawing. The line at the top names each level by its title: the processes of a place, the process, then "<file>: <step>". **default**: the processes hang only under nodes with no diagram under them, because a node with a diagram already goes down to it; a process whose first step lies in no such node is reached from the graphs of its files.
- **Order, shared boxes and columns in a drawn process** (text in `shared/process-diagrams.ts`, page in `media/process-drawing.js`). A box with two or more arrows that call at lines of its code draws them in the order of those lines, each with a quiet number before its words (`arrowPlan()`; the number stays before the words of a look, `shownFlow()`). When three or more boxes call one box, it stands once with one arrow from its first caller ("filter rows · 8 steps"); each other caller has a quiet dot at its edge (the pointer says which box it calls), the pointer on the shared box lights its callers, and its window lists them with links to their lines. An opened step whose longest chain passes 14 boxes also has `columns`: columns of at most 12 (`columnSizes()`), each a Mermaid box with `direction TB`, joined by Mermaid only as boxes (an arrow between steps of two columns would make Mermaid ignore the direction), so an arrow across columns is a dot too and the arrow from the end of a column to the start of the next is drawn by the page. A rule of a look for `layout.direction` or one that hides a box of the drawing wins over the columns; a text that does not draw falls back to the drawing of the map, with no columns. The link "One column" / "Columns" sits in the line at the top. Check: group "drawings".
- **Files**: a native tree under the changes, with the folders and files of the repo from Git. It marks the file of the tab in front (an editor, a notebook or a file tab of Apostil) when another file comes to the front, as the Explorer of VS Code does, while the tree shows. Apostil never opens the side bar by itself: VS Code's `reveal()` shows a hidden view, so the tree marks nothing while it is hidden, it marks the file in front 0.3 seconds after it shows again and only when it still shows (`TREE_SHOWS_MS` in `extension.ts`), and the steps that follow the map stop when it hides. Only a click that asks for a folder in "Files" shows it. A row that some diagram stands for has an icon at its right (VS Code shows a row's icons when the pointer is on the row or it is selected); it opens Home at the main diagram of that path, large, with the path lit (`mainStepOf()` in `home-data.ts`, `mainDiagramOf()` in `shared/repo-map.ts`): from the top map it goes one level down through the one lit node while the diagram under it has a node at the path. So a file opens the deepest diagram where it sits in a node, with that node lit; a folder whose area has a diagram opens that diagram of its inside with no node lit; a folder with none, or across several nodes, opens the diagram it sits in with those nodes lit. A path in no node of the map opens the graphs of the path. A click on a file name opens the file. "Apostil: Graphs of this folder or file" in the Explorer's right-click menu and an icon in the title bar of an open file open the graphs of the path, every diagram that it is a part of.
- **The graphs of a path**: a tab named after the path, with one small panel for each diagram from `diagramsOf()`, the widest first: the diagram drawn small with the nodes of the path lit and the rest quiet (a diagram wholly about the path is lit whole), and two lines under it: its title and where it comes from, and where the path is in it ("in: Dev server" for one lit node, "in 3 nodes", "in the whole diagram"). At 1280 px and wider two panels stand in a row, so the diagrams are larger. A panel is drawn when it comes into view. A click shows the diagram large with the same nodes lit: a map diagram on Home, a change, part or function diagram on the change page. After the diagrams of the map come the processes that have steps in the path ("process"), each drawn at its top with the steps of that path lit; a click opens that process on Home. A path in no diagram shows one line.
- **Comments on the map**: a node, an arrow and the whole diagram of a map on Home hold a comment as on the change page (the same key, outline, marks, card and list; `App` in `home.js` gives `remarks.js` and `places.js` the map in the shape of a change page; the count stands at the right end of the bar). Such a comment belongs to the repo, not to a change; `@` offers only `<app>-new`, whose run starts in the open folder. A click on its row in the list goes to that map diagram, lights the thing and opens its card. The small panels of the graphs page hold no comment.
- **Home in place of the empty editor area** (`home-when-empty.ts`): in a window on a Git repo with no tab, Apostil opens Home. It waits until no tab came for 1.5 seconds, because VS Code puts back the tabs of the last time a moment after the extension starts; a window that had tabs keeps them and gets no Home. When the last tab closes and it was not Home, Home opens again. When he closes Home itself (also among others, as with "Close All"), the area stays empty until another tab was open and closed, or the window starts again. Home that opens this way does not take the keyboard: the side bar, a terminal or a question keeps it. In a window with no folder, or on a folder that is not a Git repo, nothing opens. With a first page in the look of the repo that view takes the place of Home, and opens once when the window starts. The setting `apostil.homeWhenEmpty` (on by default) turns it all off. The icon in the Dock, the name of the app and the title of the window stay those of VS Code.
- **"on Home"**: a diagram of a change draws on a diagram of the repo, never a new one. Its field `of` names a diagram of the map or a drawing of the map (`process:<id>`, `process:<id>/<n>`), and its `before` is the text of that diagram (`repoDiagramOf()` in `shared/repo-diagram.ts`; a wider diagram with no `of` names it by its own id). Beside the title of a diagram of a part, and in the large view of a wider diagram, the quiet link "on Home" shows that diagram on Home, or the drawing of the process, without the change (`repoHtml()` in `media/diagram-stage.js`, from `onHome` of the page data). When the map has no diagram of that id, or that diagram differs from `before`, one quiet line says "The map was written again since this change was described."; the link goes with the id. Code that is all new (`new: true`) says "New in this change". A diagram of the map with `file` (a function that a change draws on) needs no `nodePaths`: its nodes stand at lines of the file, no node of Home goes down to it, and the graphs page of its file lists it.

## Marks and the look of a repo

One mechanism for both: **marks** are icons at lines of code, written by agents and rolled up to the notes, steps and nodes that hold the line; a **look** is a list of rules that a user asks for in plain words and an agent saves for one repo. With no look saved, the default look shows the marks of the built-in set `services` (the services that the code reaches) at the upper right of a node, a step and a call out of the repo, and at the left of each service line of a note.

- **Marks** (`shared/marks.ts`): the map holds `marks` (set, value, file, line, a word on the line, the text of the line at the save; for a service also a relation `calls`, `stores`, `sends` or `runs on`, and a named thing `{ kind, name }` when the code names it with fixed text) and, by set, the files that a writer read (`markedFiles`). `apostil add-marks` saves the marks of one group for one set and replaces only what that group saved for that set and the files that it names; a value is known in the set or declared once in the same JSON (a service with its name and web address, never a second id for one address); an icon (PNG, SVG, ICO or WebP, at most 100 KB, an SVG with no script, no event attribute and no outside address) is kept in the store by set and value (`icons/<set>/<value>.<ending>`), so another repo needs no new fetch; the values themselves are kept in the table `mark_value` for every repo. Its draft `apostil-marks-<group>.json` and the icon files `apostil-icon-<value>.<ending>` in the top folder are removed after a save that worked, and `apostil setup` keeps them out of Git. `apostil mark-groups --set <id> [--all]` gives the work by area, largest first, only for the areas whose notes are all saved (`waiting` counts the others, as `process-groups` does), only the files that need it (no writer of the set read them, their text changed since, or a mark of them no longer stands); for `services`, only the files with candidates, each with its candidate lines from one short list of signs (`SIGNS` in `shared/marks.ts`). `apostil marks [--set <id>]` prints the counts of each set and value, the marks whose line changed (hidden until the next run, by the rule of notes beside the code) and the icons that a website refused (`iconRefused`), and `noIcon`: the services with marks and no icon. A save of the map keeps the marks. **Icons** (`store/icon.ts`, `shared/icon-fetch.ts`): `apostil icon <service id> <https address> [--site <site>] [--other-site]` is the one command that reaches the web. It keeps the picture as the icon of the service; https only, the host is the `site` of the service or a host under it (a redirect too; `--site` names the site of a service that the next `add-marks` declares; `--other-site` only after the owner said yes), at most 100 KB of a kind that an icon may be, 10 seconds; the address of a web page gives its `link rel="icon"` or `"apple-touch-icon"`, the largest that fits. It prints `{ saved, problem }`. A service of a draft with marks, and no icon, no waiting icon and no `iconRefused` entry, is refused by `add-marks` with a sentence that says to run `apostil icon`. **`apostil map --fit`** (`shared/map-fit.ts`) prints four lists of at most 20: files with notes in no node, nodes that hold no file with a note or a process, calls of the processes between two nodes of the top diagram that have no arrow (each with an example), and the functions, methods and classes that other code files name and that have no note (`gapsIn()` in `shared/definitions.ts`; `apostil add-notes` prints the same for the files that it saved, as `gaps`, and a writer answers each with a note or a `skip` with why, kept in the map as `skips`); the skill corrects the top diagram from them (Step 6).
- **The look** (`shared/look.ts`): `apostil set-look` saves the look of the repo in the store (table `repo_look`, its files in `looks/<repo id>/`); `apostil look` prints it, or that the default applies. **One list**, `LOOK_PARTS`, holds every component that a look can change, its slots with their fields and the kind of value of each field, what a rule can pick, every target of a click, and the form of a new set of marks; the check of `set-look`, the files of a look and `apostil look-slots` all read it, so a new component, slot or target is added there, with its `area`, its `what`, its `words` and one `example`. A look has `sets` (more mark sets: id, name, rule for its writers, values, the corner where it stands on a node and on a note) and `rules`. A rule picks a kind (`node`, `step`, `call`, `arrow`, `note`, and the parts of the page of a change and of the file tab, below) and any of paths, node ids of a diagram, a mark (`set:value` or `set:*`) and a diagram id, and sets slots: `box` (colour, line colour, line width, dashed, shape), `content` (words, a picture or a film), `corners` (a set, a button with an action, or nothing), `note` (colour) and `arrow` (colour, width, dashed, a button at its label). The default look is the first rule, then a rule for the corner of each set, then the rules of the look (`lookRules()` in `look-data.ts`); for each slot of a thing the rule that names it most closely wins (a node id, then a mark, then a path, then a kind), then the later one (`resolve()` in `media/marks.js`). `set-look` checks kinds, slots, paths, node and diagram ids, colours, shapes, sets, targets and files (a picture at most 2 MB, a film at most 20 MB, standard types), and keeps each file named by its contents.
- **How the options reach the agent**: the agent reads them in layers, and only when the owner asks for another look. The prompt of the look writer says how a look works and holds no list of parts. `apostil look-slots` prints the core and one index line for each area (`areas` in `LOOK_PARTS`: diagrams, processes, notes, marks, clicks, windows, lists, blocks, pages, change, diffs, comments, file-tab, side-bar, pull-lines, files, pull-request, conversation, home, drawings, graphs, panel-lines and vscode); the core is what most looks use, marked `core` in the list (the box, the arrow without its button, the colour of a note, the corners, every pick, the forms of the targets `file`, `url`, `command`, `prompt` and `place`, `show.shown`, `content.words` and `click`; a component lists only its core slots there). An area prints a slot of another area as one line that names that area. `apostil look-slots <area>` prints one area: its components with their slots and examples, the fields with the kinds of their values, and the names of the picks; a slot comes with only the fields that the components of the area take (`takes`), and only the kinds of those values. `apostil look-slots --find "<words>"` prints the 5 best matches over the names, the `what`, the `words` and the examples (small letters, whole words and starts of words, a hit in a name counting most; no model), and with no match one sentence and the index. `apostil look-slots --all` prints the whole list. The answers are printed with each short part on one line (`compactJson()`), and their sizes are a contract that `store/look-options.test.ts` holds: the prompt and the answer with no argument at most 9,000 characters, each index line at most 110, one area at most 3,000, one search at most 2,000 (`shared/look-slots.ts`); an area that passes 3,000 is split in two, as the side bar is split into `side-bar`, `pull-lines` and `files`, and the area of the pick "where" lists the fields of the components of the core only. The list also holds what no look can use (`never`: a line above code, words in or after a code line, a tint of lines, a hover over code, a badge in the Explorer, the status bar, marks in the scroll bar, the Timeline, links in the terminal, the path above the code, the outline, inlay hints, problems under code, badges in Source Control, a count on Apostil's icon, comment threads in code, status items of notebook cells, the Testing view), each with the words that a person may use for it: when such words fit it better than any part, `--find` answers one sentence ("A look cannot use the status bar. Tell the owner so."), and a rule whose kind names it gets one sentence too. `apostil set-look --check <look.json>` checks all that the save checks, the files too, and saves and removes nothing; it prints `{ ok, problems, changes, notes }`. `changes` says for each rule how many things it picks now and what it gives them ("Rule 1: 2 nodes get a colour."), with the pick logic of the pages (the first part of `media/marks.js`, read in Node) on the diagrams of `homeData()` and the notes of the map (`store/look-changes.ts`); `notes` names each rule that picks nothing now, which is no fault. `set-look` prints the same after a save. Each sentence about an unknown name (a kind, a slot, a field, a pick, a shape, a target, a set, a diagram, a node, a command, an area) ends with the nearest right name when one is close: one or two letters changed, the same first three letters, or a name of several words that holds the word ("failing" in "checks failing"; `nearest()` in `shared/look.ts`).
- **The drawing** (`media/marks.js`, one path for a mark of any set): Home and the drawn processes apply the look when they draw (`look` in the data of Home, from `look-data.ts`: the rules, the sets, the values with their icons as data addresses, the marks that stand, and an address for each picture and film). A shape and other words go into the Mermaid text before it draws; a picture or a film takes Mermaid's picture shape with a blank picture of its size, and the real file goes in after the drawing, never into the text; the page treats `g.image-shape` as a node (`markDiagram`, `lightNodes`, the clicks and windows of Home). A film shows a frame with a play mark and plays, muted, only on a click. A missing file gives back the default box. One colour gives the colours of both themes and of the words (`boxColors()`, `lineColors()`): a pair whose words would not read at 4.5:1 is moved until they do; a high-contrast theme keeps its own colours. A diagram that the look does not change is drawn exactly as with no look.
- **Marks on a node**: a node holds the marks under its paths, a step those inside its lines, a call out of the repo those at its lines; the step that calls gets no second chip for them. An arrow of a process shows a mark at its own line, unless one of its two ends shows that mark already (the call box of that service, or the step that holds it in a corner): one service has one icon there, and the window of the end lists the use at the line of the arrow (`arrowMarks()` in `media/marks.js` decides it; a rule still picks an arrow by every mark at its line). A corner shows at most 3 chips, then "+n" as one more round chip of the same size, behind the third, so that it reads as the next service; the values that few nodes of the diagram hold come first. An icon stands on a small light round chip in both themes; an icon that fills its square is drawn to the edge of a rounded square; a value with no icon gets the first letter of its name. The pointer on a stack spreads it and opens its window (each value, its places, what the code does with it, its named things: 2, then "+n"). A click on a value goes down one level when the node has one, with the nodes that hold the value lit and the quiet line "<value> · n places in <node> ×" (the line at the top names the step); else one place opens at once, and several are listed by named thing. A set that stands in no corner of a node is listed in the window of the node. A button does its action: a file at a line, a web address after VS Code asks, a command of Apostil, a prompt to a new session of the first agent app, or a place in Apostil (a diagram of the map at a node, or a drawn process).
- **Notes**: the note cards of a file tab and the window of a step have the corners of their sets, the colour of the look as a bar, and one line for each service ("PostgreSQL · keeps data in it · 7 places") with its named things as small links (7, then "+n more"). A service icon shows in one place only: the default look gives a note no corner for the services (`DEFAULT_RULES` in `shared/look.ts`), and the icon stands at the left of its line, its middle at the middle of the first text line; in the window of a step the lines start where the text of the note starts. The marks of a file come with its code (`marksBeside()` in `page-data.ts`), with their lines now.
- **The shared kinds of every component**. Each is built once and every component that takes it uses the same code.
  - *Fields.* A component lists its `fields`, what a rule can read of a thing from the data of the page: a node `title`, `files`, `down`; a step `title`, `file`, `steps`, `is` (step or process); a call `name` (the names that the code calls it by), `of`; an arrow `words`, `of` (the node it comes from); a note `title`, `file`, `function`, `tests`. The pick `where` (`{ "<field>": <value> }` or a list of values) picks by them and ranks after a path and before a kind. `takes` names the fields of a slot that a component takes; the check says so in one sentence ("a node cannot be folded. A node takes only "shown"."), and a wrong name gets the nearest right one (`nearest()`).
  - *What shows and the words.* `show.shown: false` leaves a node, a step, a call or an arrow out of the Mermaid text with its arrows before Mermaid draws (`shownFlow()` and `flowWithout()` in `media/marks.js`, which count the arrows as `flowGraph()` does; a statement that names nothing hidden stays as written, and a group left empty goes), and a note card out of the column of notes; counts elsewhere keep counting it. `content.words` may hold fields in braces (`"{title} · {files} files"`, `fillWords()`; text from the repo is escaped), also on an arrow, and `content.fields` orders the fields of a note card (title, function, tests, text, services) and leaves out the others. `text` gives the words a colour (an arrow), a size (small, normal, large) and an icon before them (a node, a step, a call): the size and the place of the icon are Mermaid classes there while it measures. `order` (by, down, group, first) and its one function `orderRows()` order the rows of a list; a list takes each field of `order` that a rule gives one of its rows (`listOrder()`), and `shownInOrder()` gives the rows that a list shows in that order (the files of the list of diffs, the threads and the open points, the views, the diagrams of a part, the notes, the rows of the list "Repo", the folders of the tree, the checks, the side column, the look of the conversation, the panels of the graphs page).
  - *One list of targets.* `LOOK_PARTS.targets` (a button keeps its field `action`) holds every place a click, a key or a menu entry goes: `file`, `url`, `command`, `prompt`, `place`, `graphs`, `folder`, `change` (with `part`), `pull` and `comment`. A command is one of `LOOK_COMMANDS` (the commands that open or change a view); the save refuses the commands that set up agents, install the command, connect Claude Code, uninstall or turn links off and on, and the extension runs no other. One `act()` in `media/marks.js` serves every page: the comment box opens on the thing, a place or the graphs of a path open as a step of the path when the page can take it (`Marks.useHere()`), and the rest goes as one message `target` to one function in the extension (`answerTarget()` in `look-targets.ts`), which asks before a web address opens and shows a prompt whole with "Send" before it goes, also from a note card. `package.json` declares no `capabilities.untrustedWorkspaces`, so VS Code keeps Apostil, and every look, off in a workspace that it does not trust.
  - *A click and other input.* `click` is one target in place of the default click (a node, a step, a call, the words of an arrow, a note card). `input` has `alt` and `shift` (a click with that key held), `double`, `key` (a letter or a digit while the pointer is on the thing or it has the keyboard; the keys that a page uses already, `PAGE_KEYS`, are refused with the free ones) and `menu` (rows of a small window on a right click, in the frame of `hover-window.js`). Only a thing with a double click waits a quarter of a second before its single click (`bind()`). The pointer says what a click and each other input do, one line each (`inputWords()`): at the top of the window of a node or a step, and in a small window on the words of an arrow and on a note card.
  - *The window of the pointer.* `windowOf()` builds a window from named sections; `nodeWindow()`, `noteWindow()` and `stackWindow()` use it. Where the cards of the overview show, a node of Home or a part of a change with a card has its window only with the slot `window` (`Marks.hasWindow()`, as a note card) or, on Home, marks in no corner; else only the small window of what its click and other input do (`inputWindow()`), when a rule gives them. A step keeps the window of its note. A node has `files`, `changes`, `marks`; a step and a call `note`, `where` (the quiet line of the title), `marks`. The slot `window` gives a `width` and the `sections` in their order; a section that it does not name is not shown, and a section of its own (`{ "title"?, "blocks" }`) stands at its place among them, outside the frame of the built-in sections (`ownSection()`).
- **Blocks, windows of blocks and pages of the look**. A look says *what* a window or a page shows with blocks, and Apostil draws them in its own style, in both themes; the agent writes no HTML and no script, and blocks stand only in Apostil's own pages and windows, never in VS Code's editor.

## The line at the top

- **The path that he followed**: Home, the graphs page and the change page show one line, the views that he went through to come here in the order he took them, the last one bold. It always starts with "Home" (the top map). A step is a view: a map diagram on Home, the graphs of a path, a change, the diagram of a part, a wider diagram in its large view, "Diffs". A file is not a step; a file tab has no line.
- **One path for the window**: the extension keeps it (`trail.ts`, with the rules in `media/trail.js`, which the pages use too) and sends it with the data; a page tells it each step that it takes. Only a tab that shows gets a new path; a hidden tab gets it when it shows, because a message to a hidden tab just before a new tab opens takes the keyboard focus from the new tab. Opening something from outside a page (the side bar, the Files tree, the Explorer, a title bar, a command) starts a new path, `Home › that thing`. A step that is in the path already cuts it back there.
- **Back and forward**: a click on an earlier step shows that view again in its tab, with what was lit there, and the path ends there. Cmd+Left goes one step back and Cmd+Right one step forward, as in a browser (Ctrl+Left and Ctrl+Right off a Mac, where VS Code uses those keys only in a text field; Alt+Left and Alt+Right everywhere; one listener at the end of `media/trail.js`), on Home, the graphs page, a page of the look, the page of a change or of a pull request, and a file tab. The path keeps the steps that a way back left (`ahead` in `trail.ts`; `goTo()` and `next()` in `media/trail.js` are the rules), and a new step drops them. A file tab is no step: it stands after the last step, so back shows that step. In a text field the keys keep their meaning. Inside VS Code the page only says which way (`move`), and the extension finds the step. Too long for its width, the middle steps fold into "…"; a click on it shows them.

## The change page

- **One card**: the diagram of the change, with its total diff in the title row, and after it whether a second agent read its links ("checked" or "not checked yet"; nothing for a change with no link), and one quiet line under it, "alters: <wider diagram> +2 parts", one link for each wider diagram that the change alters; a wider diagram that it does not alter follows as "wider: <title>". The link shows that diagram large, with the difference painted in.
- **The code beside the diagram**: from 1040 px wide (`SPLIT` in `media/split.js`), when the page still has 840 px for two halves of 420, the diagram page is two halves, the code at the left and the diagram at the right. Each half scrolls by itself, and the page does not scroll. Below that width the page shows the diagram alone. A diagram too large for its half opens at a size where its words read (85%), at its start.
  - **The page of the change**: the left half is a list of closed diffs: under the name of each part, each file is one row with a small mark, its path and its counts (`diffList()` in `media/split.js`). The folds of "Diffs" stay: "57 more files in …", and a data file or a generated file says so on its row. A click on a row opens its diff below it, with the notes beside it, in a short animation of its height; a click on its head closes it. The name of the file still opens its tab. The diff and its node find each other both ways:
    - The pointer that rests on a row or an open diff (the delay of a hover window) marks the node of its part (a darker border) and lights the line of its file there in a short animation; a pointer that only crosses rows moves nothing. A file that the node does not list stands in place of "5 more files" while it is pointed at, or while it is the last one opened. When the node is outside the visible part of the diagram, the diagram moves to it.
    - The pointer that rests on a node (the delay of a hover window) brings its part to the top of the list and opens the diffs that show under it (not the folds). The pointer on one file name in a node opens only that file. The diffs that the pointer opened close when it rests on another node; a diff opened with a click, or clicked in, stays. Leaving the diagram leaves them as they are.
    - No window opens on a part, a file name or "5 more files": what it would show is at the left. A click on a part with a diagram opens it; a click on a part with no diagram, or on the row of a file in a node, opens that diff in the list (a part: its first file), and the diagram half keeps what it shows (Cmd+click on a file name opens it in the editor). A click on "5 more files" opens a window in the diagram half with every file of the part and its counts, each a link that brings its diff to the top of the list, and the list brings the part to its top.
    - **A link between parts** has its code (`links` in the page data, from `linkThings()` and `pageCodes()`). A link with a diff has its counts just under its text, or at the middle of its line when it has none; it is not coloured. The pointer that rests on a link, on its text or its line: when its places are all changed lines of one file, that diff comes to the top of the list, opens at those lines (or with its head at the top when the lines fit under it), and their rows light; when its places are in several files, on lines that the change did not touch, a whole file, or it has an open point, they show one under the other over the list, each with its file name and two rows around it. A click keeps it; a click elsewhere in the diagram, or resting on a part, lets it go. A link with a reason shows the reason in a small window. With the code hidden, or below 1040 px, the pointer on a link opens a window with its places or its reason, and a click opens its first place. An open point at a link is the small ring with "?" at its text (or at the middle of its line), its text stands with its places, and it is listed under "Open points".
    - J and K open the next and the previous row at the top and close the one that the keys opened before. Alt+Down and Alt+Up step through the changes, and the graph follows (below).
    - Each animation takes 0.2 seconds (`MOTION_MS` and `glide()` in `media/tools.js`); none runs when the system asks for less motion.
  - **The page of a part, for a diagram with `file`**: the left half shows that file as a file tab does, so the diagram stays at the right when he goes into a part (the whole file, added rows green, removed rows red in place, long lines that wrap), opened at the lines of the diagram. Its notes are marks at the right edge. The head names the file with its counts; a click on the name opens the file tab. **The code follows a click, not the pointer**. The pointer on a step only lights it after the delay, and lights its rows with one line from the left edge of the step to the right edge of its rows when they are in view already; it moves no code and opens no window. A click on a step (an arrow, a message, a transition, the same way, by its label, its counts or its line; a "yes" or "no" out of a decision lights the rows of the decision, and a removed thing lights its red rows) brings the first rows into view and keeps the step lit until the next click; a thing with a place in another file, a whole file as a place, or an open point shows its places one under the other over the file (each with its file name, its lines and two rows around them; a whole file with its head and counts) until the next click. Cmd+click opens the file as a tab, and so does "Open" in the window of a step; with no code half (a narrow tab, "Hide code") a click opens the window of the step. The pointer on rows of a thing lights the thing. A thing with a reason shows the reason in a small window ("Outside the repo.", "Only the order.", "No line of its own."); nothing else marks it. The changed lines of the code that the diagram covers that are in no node and no arrow have a quiet mark at their number.
  - **The page of a part, for a diagram with no `file`** (a sequence across files, the states of a field): the left half is the same list for the files of the part, all open when they are three or fewer, with no joins.
  - **"Hide code"** stands over the code, at the right end of the line of the first group header of the list (in the head of the file beside a diagram with a `file`), with "Open all" or "Close all" before it; they stay there while the list scrolls (`Split.controls()`). With the code hidden, "Show code" stands at the left of the line above the diagram, whose right end keeps the stepper. It brings the code back. The choice lasts for every change (`keep()`; as a file in a browser, in the storage of the browser).
  - Comments work in the list as in a file tab: on a row, on a range, on a note of an open diff. A comment or a point on a file whose diff is closed is still in the list of the comments, and a click on its row opens that diff at its lines.
- **What the change did to a diagram of a part**: a node is not coloured; only its diff is. A node with a diff shows its counts where its line number stood ("+3", "−2", "+1 −1"), in the green and red of the code rows; a node with no diff keeps its line number ("lines 12–20"), its file name for a whole file, or "3 places"; a node with a reason shows nothing there. A removed step is back in, where it was as near as can be, with a dashed border and quiet text. An arrow, message or transition is not coloured either: one with a diff has its counts beside its text, and a removed one is dashed, with quiet text. The text of an arrow that the pointer is on, or that a click keeps, is in teal with no box around it, as a message is. One quiet line beside the title says the total in words that fit the kind ("+2 steps −1 step · 1 changed"; messages for a sequence; states and transitions for a state diagram). It is the only legend. A diagram whose nodes are all new counts them ("+10 steps"); a flow chart of a file that the change added is new in each step. The facts come from `before` and from the code lines of the nodes and arrows (`shared/diagram-change.ts`); a diagram with neither shows no change. The same marks show on the page of the part, in the diagram of the change after drill up, and in the window on a part. A text with the removed things that does not draw is drawn as the diagram of now, with the marks that need no removed thing. A wider diagram keeps its own look.
- **The window on a thing** (narrow, after drill up, in the window on a part) shows its places one under the other, each with its file name and the rows of its lines, added rows green and removed rows red in place; or its reason.
- **A schema diagram** (the kind `schema`, for a change to a file that builds a schema) is drawn by the page, not by Mermaid (`media/schema.js`, from `schema` in the page data, `schemaDrawing()` in `shared/schema.ts`). A table is a box with its name in the head and its rows of columns: the name at the left, the type at the right, ◆ for a primary key and ◇ for another key. A relation is a line from the row of its column, or from the head when it names none, to the key or the head of the table that it points at; between the two columns of boxes it goes across, inside one it bends round the outer side. The tables that the change touched come first, each in the shorter column; a table for context goes to the column of the tables it is related to. A table with more than 10 columns shows 8 and "13 more columns", which opens the rest in place with a click. An added table or column has "+" in green, a removed one "−" in red and a dashed border, a removed column is struck through, a changed column shows its old type struck through before the new one, and the counts of a table stand in its head. A table that the change does not touch has a quiet name. Nothing is coloured by the change. The drawing has the form of a Mermaid flow chart (a table is a `g.node` whose id names it, a relation a path `L_<from>_<to>_<n>`), so the marks, the counts of a relation, the join to its lines, the lit things on "Diffs", a comment on a table or a relation, the small panels of the graphs page and Home use it as they use any diagram. The total beside the title counts tables, relations and columns ("+2 tables −2 tables · +6 relations").
- **Beside the title of a diagram of a part**: after the total of the change, one quiet count of the changed lines that the diagram covers and that are in no node and no arrow ("10 changed lines in no step"; "in no message", "in no state or transition"), and whether a second agent read it: "checked" or "not checked yet". A description with no record of a check says "not checked yet". An open point at a node or an arrow is a small quiet ring with "?" on the thing, its text stands with the places of the thing ("Check: ..."), and it is listed under "Open points" in the list of comments. The code of each thing and its diff (the sum over its places) come from `thingsOf()` and `thingCounts()` in `shared/diagram-code.ts`; the page data builds them once (`partDiagram()` in `page-data.ts`). A removed thing shows its own "−N"; those removed rows do not count on the thing that stands there now.
- **Parts with no arrow** stand in rows of three or four, so their words keep their normal size (`gridLinks()` in `change-diagram.ts`: invisible links from each node to the node under it). The box "In no part" counts as one of them. Up to four stand in one row. Parts with arrows keep their layout.
- **A change of one part**, with no file in no part, opens that part at once: its diagram when it has one, else the code of its first file with notes. The line at the top still leads back to Home. The first view of the switch stays on; it says "Diagram", or "Code" when the part has no diagram.
- **The diagrams of a part** are named in the quiet switch by what they explain: the function when each diagram has its own, else the title, cut at 40 letters, with the kind after it as a quiet word ("renew_loan flow · place_hold flow"). Named by function, the full title follows them.
- **A diagram is a surface**: a drag, the wheel and a scroll with two fingers move it, a pinch on the trackpad and Cmd+scroll zoom at the pointer (in a stack of diagrams a scroll that the drawing cannot take scrolls the half), and a double click on an empty place fits it whole to its card. A map on Home or a wider diagram so wide that fitting it to the width would make its words smaller than 11 px opens at the smallest size where they read (85%), at the start of its flow: its left end when it goes from left to right, else its top in the middle. A drag starts after the pointer moved 4 pixels, so a click on a part or a file name still works. The card takes the height that is left in the tab (in the overview, the upper part of it). The same holds for the large view of a wider diagram and of a part's diagram.

The icons at its corner stay where they are: grown, they would move away from a pointer that rests on their edge, and shake. A node that opens nothing does not grow, and no node does under the comment pointer, where a click sticks a comment. With "reduce motion" set, the node has the larger size at once.
- **One run for one shortcut**: a shortcut such as Cmd+B runs once. When the keyboard goes from one page of Apostil to another (the list in the side bar and a tab), the switch can end off, and then the menu runs the shortcut a second time. In a check window the switch ended off in 11 of 24 moves of the keyboard between the list and Home; the second run itself needs a key of a real keyboard, which no check can press. The window check presses Cmd+B with a file tab of Apostil in front: the side bar hides and stays hidden for a second; shown and hidden at once, it stays hidden (see "Files": a mark of the tree would open it again); and the key shows it again.

The drawing of a process in columns and the same in one column are two drawings: each fits when it first shows. A drawing that kept its view is not moved to a lit node.
- **The key of a drawn process**: quiet rows in the top left corner of its frame, one for each kind of box that it shows: "a step here" (solid), "a step it calls elsewhere" and "outside the repo" (dashed), and "1 2 3 the order of the calls" when an arrow has a number (`ProcessDrawing.key()`, `.pd-key` in `look.css`). A drawing with no dashed box and no number has none; a written diagram has none.
- **Words that fit their box**: Mermaid sizes each box by the words it measures. A drawing waits for the fonts of the page first, and one whose words come out wider than their box is drawn once more (`wordsOverflow()` in `media/diagram-stage.js`).
- **Focus on a node**: one click on a node of a diagram whose nodes lead somewhere (Home at every level, a drawn process, a panel of the graphs page, a part of "Diagram" of a change or a pull request) lights the node, its arrows and the nodes at their other ends, and the rest grows faint (`focusNode()`, `focusOn()` and `focusClicks()` in `media/diagram-stage.js`, the classes `focus`, `tied` and `focused` in `look.css`). Option+click does the same. A click on another node moves the focus there. Where the cards of the overview show, one click focuses the node and its card: the card gets an accent edge, the other cards grow faint, and when no part of the card is in view the page scrolls to it, smoothly and as little as it can (at once with "reduce motion"; `Overview.focused()`). A click on the node that has the focus, or a double click on a node, goes into it, as its card does, with the cards or with the diagram alone: one level down, or at the last level its code (one file opens, folders open in the tree "Files", a step opens its file at its line); on the graphs page the panel opens; beside the list of a change the part comes to the list (`tie.click`). A double click on a node never fits the diagram; on an empty place it still does. The rows inside a node or a hover window (a file, "5 more files", a mark) and the cards of the overview keep their one click (`IN_A_NODE`). One quiet line in the head, after the path, says "Focus: <node> · ×": on the line of the path, so nothing under the pointer moves when it comes. The ×, Escape (when no window is open and no text field has the keyboard) or a click on an empty place of the frame or between the cards ends it, for the node and its card. The same diagram drawn again keeps its focus; another diagram has none. A look that gives the click of a node a target, or `input.alt`, `input.shift` or `input.double` (on the graphs page: to its panel), wins. A panel of the graphs page takes no pointer itself, so there the place of the click finds the node (`nodeAt()`); a panel of a change, a part or a function has no graph on that page, so the click opens it. The line names a step without the count of its steps (`plainName()`). Both count as arrows of the node (`graph.dots` and `path.colink` in `focusNode()`), and the dots of a faint box grow faint with it.
- **While the wheel moves or zooms**, no hover window opens over the diagram, also when the pointer is on a node.

A close from outside while a window waits its 0.3 s stops that wait, and the next real move on the same thing asks again (`waiting`: one element owns the one open timer). A window closes 0.25 s after the pointer leaves it or its thing; only one such wait runs, so the next enter keeps it open also when the pointer crossed both edges (`hideSoon()`).

On the rest of a diagram it is the open hand that moves the diagram: an empty place, an arrow, the box "In no part", "more files", the inside of a frame.

The current change is the change that the last key made current, while the list stays where the key put it; else the run of changed rows at the line, else the next run below it in that file, else the last run of the file. Over closed rows it is the first closed row in view.
  - **The rule of a step** (`stepPlace()` in `media/code-notes.js`, one rule for every place that shows a diff):
    - A change within reach comes to the reading line: the list glides by no more than its height less two rows, so the last two rows of the view before stay in the view.
    - A change out of reach: the list moves by exactly its height less two rows (under the name of the part and the head of the file that stick at the top). The last two rows of the view before are then its first two rows, and the next key goes on from there. So a change taller than the view is read with the same key, with no row passed over; the last change of a file is read to its end first, and the next file is opened only then.
    - The change that a key went to is the current one as soon as its first row is in the view, also when it is not at the reading line. While a long change is read and the next one is not in the view yet, the long one stays current.
    - A step into the next file brings the head of that file to the top, under the name of its part, as J does.
    - Alt+Up is the same, turned over. A step into the file above makes its last change current: its first row comes to the reading line when the change ends inside the view, else the last row of that file comes to the bottom.
    - With no next change, nothing moves once the last change is read. A second key while the list glides counts from the place where the glide ends.
    - A file whose rows are not filled yet is filled first; a folded file (generated, data) and a file with no text are passed over; a step that reaches "57 more files" opens it. The keys do nothing while he types in a field.

A change in no thing keeps the diagrams and lights nothing. A click on it: when the list holds all its places, its first place comes to the reading line (a closed diff opens first) and the rows of its places light; a place that the list does not hold, a whole file as a place, or an open point shows its places one under the other over the list, as on the page of a part. A click keeps the thing; a click elsewhere in the diagram half lets it go.   - The page of a part keeps its file at the left and its own steps. On a narrow tab, and with "Hide code", the page is the diagram alone.
- **"Diffs": the list of the files at the left, the file with its notes at the right** (`diffsPage()` in `media/split.js`).
  - The list is the list of diffs of "Diagram" as closed rows, under the names of their parts, with the name of a part staying at the top (`drawDiffs()` with `rows`). A row never opens: no small mark, no diff. It is 300 px wide (`LIST_WIDTH`). A row is one line: the folder of the file, quiet and cut at its left end ("…/generated/model/reservation.ts"), the name of the file and its counts at the right; the whole path is in its tooltip. A generated file, a data file and "57 more files" look as on "Diagram". The row of the file that shows is marked (teal at its left edge) and comes into view when the file changes. A click on a row shows that file: a file drawn before comes back at once, at the place where he left it; a new one at its first change.
  - The file is **the file view** (`fileView()` in `media/code-notes.js`, the same code as the file tab): the whole file, with a head that names it with its counts (a click opens its tab), its changed rows marked, and each note as a card beside its lines when the half has 720 px (`NARROW`), else a mark at the edge. A file with no text shows what the file view shows for it. A new width of the half (the tab changes its width) draws the file again with the same line at its top.
  - **The keys**: Alt+Down and Alt+Up step through the changes of the file by the rule of a step (`fileSteps()`, as in a file tab). After the last change of a file the key goes on to the first change of the next file of the list with a change, and Alt+Up from the first change to the last change of the file before it; a folded file and a file with no text are passed (`nextChange()` over `changeCounts()`). J and K show the next and the previous file at its first change. The counter at the right of the line of tabs counts over the whole list ("file 10 of 40 · change 15 of 79"), and its arrows do what the keys do; "file 10 of 40" lists every file.
  - **The width**: the list beside the file from a tab of 800 px (`FILES_SPLIT`) when the page still has 720 px for the list and a file of 420; the diagram page keeps its own 1040 px (`SPLIT`). The cards show from a file of 720 px.
  - **"Hide files"** at the right of the line of tabs hides the list; "Show files" brings it back. It lasts as "Hide code" lasts. With the list hidden, and on a narrow tab, "Diffs" is the file alone with the counter, and the list of every file is behind "file 10 of 48", as in a file tab.
  - A pull request with no described change whose commits are in the folder has the same two halves, with no notes.
- **A hidden tab draws nothing**: when the page has no layout (a hidden tab), a drawing waits and is made when the tab shows again. Mermaid measures every label as empty in a page with no layout, which left the page blank with stray lines.

## Notes beside any code file

- **A code file that opens the normal way has its notes**, with no click: the editor of VS Code stays as it is, and the notes stand in it. A note shows when its lines are still in the file with the same text. The notes come from every described change of the repo, open or merged, also after the branch was squashed and deleted. One rule finds them, with no `vscode` import: `shared/notes-beside-code.ts`. The editor, the file tab and the tests all use it.
- **The rule**: the save keeps the text of the lines of each note (`noteCode` of a stored change). For a file, the rule looks for those lines in the text as it is now, as one block with the same text; spaces at the end of a line do not count. When the block is there more than once, the place nearest to the old line numbers counts. When it is not there, the note is older than the code and does not show. A change saved before the save kept the text reads it from Git at the commit of its save, while Git has that commit; else its notes do not show. The same note from two saved changes (a stack, a branch saved again) shows once, the newest. The text in the editor counts, also lines that are not saved yet: after an edit the notes move with their lines. When the cleanup removes a change, the store keeps its notes and their text (`kept_notes`), so they still stand beside the code.
- **In the editor of VS Code** (`notes-beside-code.ts`): the title of each note as quiet text, with no box, at the end of the first line of the note. A file can have 40 notes and more, with a step inside its function, so the editor stays calm: one title on a line, and one marked note at a time. The pointer on a line shows the narrowest note that holds it (a step, not its function), and on the first line of a note also that note: its title, its text, its function and its test count, its linked tests, the change or the map it came from, and "Open in the file tab of Apostil". The note under the pointer gets a thin teal line at the left of its lines; no other note has one (`markOf()`). The colours are theme colours of the extension (`apostil.noteLine`, `apostil.noteTitle`), with values for light, dark and high contrast; a theme can set its own.
- **The line of the title**: the first line of the note. When notes start on one line, only the narrowest has its title there; the pointer on that line shows the others too (`titledNotes()` and `notesAtLine()` in `note-lines.ts`). A title longer than 60 characters is cut; the pointer shows the whole note.
- **Cmd+Shift+,** (Ctrl+Shift+, elsewhere; the key beside the comment key) hides the notes of this tab and shows them again. It holds for this tab only: when the tab closes, the file opens with its notes the next time. The key works only when the file in front has notes; else VS Code's own command of that key ("Replace with Previous Value") stays. A quiet count in the status bar says "4 notes", "4 notes hidden" and "1 older than the code"; a click on it does what the key does. A file with no notes shows nothing of Apostil.
- **The setting `apostil.notesBesideCode`**: `tab` (the default) opens a file that has notes in the file tab of Apostil by itself, with each note as a card beside its lines, unless the file has edits that are not saved; the key changes that one tab to the editor and back, and the file tab then opens at the line he was on. A file that opens at a line (a search result, "Go to Definition", a line after its name in Quick Open) opens the file tab at that line: the tab opens at the line known at once, and a place of the cursor that VS Code tells a moment later goes on to the tab while the editor still stands (`follow()`), with no wait. The start of a file tab (its lines, or its first or last change) stays with its view until its page is ready (`takeStart()` in `page-data.ts`): a load of the data while the page still loads does not use it up. A notebook is the one file that keeps its own editor with `tab`, with its notes in its cells, because the file tab cannot run a cell. `editor` is the compact way: it puts the notes into the editor of VS Code. `off` shows no notes beside the code.
- **What the editor of VS Code does not let an extension do**: place a view beside the lines of its editor. So there is no column of cards at the height of their lines, no line from a note to its code, no arrow from note to note, and a title is one line of text with no wrap and no font size of its own. The stable interface gives text after a line, a line mark, a mark at the right edge, a hover and the status bar; Apostil uses those, and no proposed interface. The column waits for the fork.
- **A notebook in the notebook editor of VS Code**: a notebook that opens the normal way shows its notes in its cells, with the same marks: each cell has a text editor of its own, and the marks of a note go into the editor of the cell that holds its lines. The rule reads the notebook as the text of its cells (`shared/notebook.ts`), from the notebook editor with the cells that are not saved yet, so a cell put in above moves the note with its cell. The pointer on a noted line of a cell shows the whole note, with "cell 5, lines 2–3". The key, the count in the status bar ("2 notes", for the whole notebook) and the setting hold as for a code file; with the setting `tab` a notebook stays in the notebook editor until the key. Nothing of Apostil starts a kernel, runs a cell or changes the notebook.
- **What the notebook editor does not let an extension do**: a text cell (Markdown) shows as a formatted page and has no text editor until it is edited, and the stable interface gives no mark on that page; so a note on a text cell shows only while that cell is edited (a double click), and the count in the status bar still counts it. The marks of a note in a code cell are the marks of a code file; a note whose lines run over two cells is marked in each.
- **Not built**: notes on a file that is not in a Git repo, and notes in a diff editor of VS Code.

## The file tab

- **A click on a file name** opens the file as a tab of its own in the group of the page: a read-only custom editor (`apostil.file`, priority `option`) for the real file, so the tab has the file's name and icon. A second click shows the open tab. A file that the change removed stays on the change page.
- **The whole file, nothing above it**: every line, as in an editor; added lines have the added background, and the lines that the change removed stand in place with the removed background. Only the rows in view are drawn, inside a block with the height of the whole file, so a file of 7,500 lines opens at once and its scroll bar is right from the start. Code is never cut off, and nothing scrolls sideways: a line longer than the box of the code wraps, at any character, and goes on at its indent plus 2 characters. The line number and the sign stand beside the first visual row. Tabs are 4 wide.
- **Rows of different heights**: the font is monospace, so the visual rows of a line follow from its length and the width of the box (`Wrap` in `code-notes.js`); the width of one character is measured once. `virtualRows` adds the heights up: the top of a row is the sum of the heights above it. The scroll to a line, the change in view, the place of each note and its join all use these sums. A row that is drawn taller than worked out (a wide character) keeps its real height. When the box gets another width, the heights are worked out again and the line at the top of the view stays at the top (`Code.fit`).
- **The small code map** (`codeMap()` in `media/code-map.js`) stands at the right edge of the box of a whole file, left of its scroll bar, as VS Code has it beside its editor: each row of the file is a row 2 px high, each piece of it a bar 1 px wide for each character, in the colour that the code view gives it (the pieces are read from the same coloured HTML, `lineColors()`), wrapped as the code wraps. Its places come from the sums of `virtualRows`: the map is the box of the code at a scale of 2 px for one row. It is drawn on a canvas, and only the part that shows. The part in view is a soft box (the colours `minimapSlider` of VS Code, at half strength at rest), stronger under the pointer and while it is held; a click shows that place in the middle of the box, a drag of the box scrolls, and a wheel on the map scrolls the file. A file taller than the map moves the map with it, so its top shows at the top of the file and its end at the end. A thin teal mark at its right edge stands for the rows of each note, and added and removed rows have the faint colour of their rows. Wide, the map is 120 px and lies under the right end of the column of the notes: the cards lie over it, whole, with their lines; where no card stands, the map shows, and the last 10 px at its right always show. The column keeps its width, so the code keeps its width. Narrow, the map is 60 px at the right of the marks, so no mark lies on the map. A file with no notes has the map in a column of its own. It sticks below the control of the files. With the setting `editor.minimap.enabled` of VS Code off there is no map; the extension sends the setting with the data of the page, and a change of it shows or hides each map in place (`minimap`). The file beside the diagram of a part and the file of "Diffs" are the same file view, so they have the same map.
- **"Edit"** in the control of the files at the top right changes the tab to the editor of VS Code, at the first line in view, with the keyboard in the editor; a double click on a line does it at that line. It is the same change as Cmd+Shift+, (`apostil.toggleNotes`, which takes the file and the line), and the key brings the file tab back at the line of the cursor.
- **The notes** stand in a column beside the code, each at the height of its first line, and never over the code (`cardPlaces()` in `code-notes.js`, one rule for the file tab, "Diffs" and the page of a part). Where the cards of a stretch do not fit at their rows (a note for each 4 lines), they show their title on one line; the pointer on a card or on its rows opens it to its whole text over the cards below it, and no other card moves. The focused note (a click on its card, or the step that a focus on Home follows) stands whole instead and moves the cards under it down, so it covers none; a click anywhere else in the file ends the focus (`keep` of `cardPlaces()`). Where even the titles do not fit, a card stands lower than its row. A line joins each note to the middle of its code lines. A step inside its function (a note whose lines lie inside another note) stands one lane in under the card of its function, and the card of the next function stands at the left again; the function is the head of its steps, and its line joins its first row only (`lanesOf()`). The notes of one function in a change are its numbered steps: an arrow goes from each to the next (`noteLinks`). The pointer on a note lights its lines and its line, and the pointer on lines lights the narrowest note that holds them (`narrowestAt()`): a row of a step lights the step, a row of the function in no step lights the function. The box of the code ends where the notes begin. A note of a wrapped line stands at the first visual row of its first line. The first note of a function names it with its test count ("3 tests"); above 20 tests the count says "many tests", and its window lists them only after a click on "Show them". A note shows its own linked tests. Below 720 px of column the notes fold to marks at the right edge, and the pointer on a mark shows the note as a window. The mark of a step stands beside the mark of its function, in its lane, so no two marks lie on top of each other. A file of 1,500 lines with 150 notes places its cards in about 3 ms.
- **A notebook** (`.ipynb`) shows as its cells, one under the other, in the file tab, on "Diffs" and in a hover window: a quiet head row for each cell ("cell 3 · code · id fee", "cell 4 · text"), then its lines, numbered inside the cell. A text cell (Markdown) shows its text as written, with no colour of code. An output is not shown; a cell that has one says "output not shown" in its head. The head says what the change did to a cell: "new", "removed", "changed", "moved from cell 6", "moved to cell 2"; a changed cell has one head over its removed and its added rows. The rows count in the text of the cells (`shared/notebook.ts`), so the notes, the places of a diagram, the join both ways, the marks, Alt+Down and Alt+Up and the drawing of only the rows in view work as for any file (`cellRows()` in `code-notes.js`, from `cells` of the page file or of the answer to `code:<path>`). A notebook in which only outputs or run counts changed is one folded row, "only outputs changed"; a `.ipynb` file that does not read as a notebook shows as text, with "does not read as a notebook, shown as text" beside its name.
- **A note on removed lines** (`"removed": true`) looks and works like any note: its card stands at the height of its first removed row, joined to the middle of its removed rows. A file that the change deleted shows all its lines as removed rows, with its notes beside them; it stays on the change page, since VS Code has no file to open as a tab.
- **One part of the code for "code with notes"**: `codeWithNotes()` in `code-notes.js` draws the rows, wraps them, places the notes and lights them. The file tab, each file of "Diffs" and the hover windows of a diff, of code lines and of tests all use it. A row of a removed line counts in the file as it was; every other row in the file now (`spanOf`).
- **A very long line** that takes more than 8 visual rows shows its first 8 rows and "Show all 30,000 characters"; the click shows all of it.
- **A file with no text to show** says what it is in one line: "Binary file, 4 KB", "Empty file", "Link to src/app.py", "Only the mode changed: now executable". A picture shows as a picture; a changed picture shows before and after side by side. The same holds in a file tab, on "Diffs" and in the hover window of the file. `page-data.ts` finds these facts once for each page (`describeFiles`), and sends a picture only when the page asks (`picture:<path>`).
- **A renamed file** is one file with "renamed from <old path>", and only its changed lines are marked. A part that names the old path lists it once, under the new name; the summary line says "1 file named by the old path".
- **The colour of a note**: a note has the colour of its code. Beside added lines its card, its join line and its narrow mark are green as the added rows; beside removed lines they are red as the removed rows; a note on lines that the change left alone is plain (`toneOf()` in `code-notes.js`).
- **The notes of other changes**: the file tab also shows the notes of every other described change of the repo whose lines are still the same, by the rule of `shared/notes-beside-code.ts` (they come with the answer to `code:<path>`, `notesBeside()` in `page-data.ts`). Such a note has no colour of added or removed lines, and its card says "From “<the title of its change>”". The notes of the map come the same way; their card is the title and the text alone, since a note of the map is about the code as it is now. The hover in the editor still says where a note came from. A comment on it is a comment on its lines. When the branch has no stored change, the file tab shows the code as it is, with no diff and no control of the diffs, and these notes beside it (`filePage()`).
- **Where a file opens**: at the lines that were asked for; else at its first change, when that change is below the first screen (a file of 2,400 lines with one change at the end does not open at line 1); else at its top.
- **Going through the diffs**: a quiet control at the top right says "file 4 of 47" with ‹ and ›, and "change 3 of 12" with ↑ and ↓. J and K open the next and the previous changed file; Alt+Down and Alt+Up go from change to change by the rule of a step of "Diffs" (`fileSteps()`): the reading line a third down, the glide, the two rows that stay. Rows of a whole file between two changes that would fill a view with no changed row are passed: the next change comes to the reading line. After the last change of a file a key opens the next file, at its first change (Alt+Up: the file before, at its last change). The counter is the counter of "Diffs", counted in the file: at its top it names the first change, the one below the reading line. The file beside the diagram of a part steps through its changes by the same rule and stops after its last change, since the next file would leave the diagram. A jump to the lines of a note or a comment is no step: those lines come three rows below the top. The next file opens in the same tab, in the order of the parts, the files in no part last, the generated files left out. A click on "file 4 of 47" lists every changed file under the names of the parts, with its counts.

## Comments

A comment is a card at its place, and the page has its full width.

- **The mark** of the open threads of a thing is a chat bubble with the icon of the agent app that has them (`view/media/agents/<app>.svg`), in the state of the newest thread (`markState()` and `markHtml()` in `states.js`): sent and waiting, the icon faint; working, a small teal dot at its corner, still; answered and not read in its card yet, tinted with a teal edge; a note to no agent, empty; resolved, no mark. Two or more threads on one thing share one bubble with a small count. It stands after the text of an HTML thing (a part, a file row, a title row, a note), at the top right corner of a drawn box, beside the middle of the line of an arrow with no words, at the end of the text of the first line of code lines, and at the end of the name line of a message of a pull request. The mark of a part also counts the threads on its files and on code lines of its files. Its colours are its own (`--cb-fill`, `--cb-edge`), so the rules of Mermaid inside a node do not paint it; inside a node the label lets the mark of a file row show past the measured words (`g.node foreignObject{overflow:visible}`).
- **Menus close on a click elsewhere**: the menu of where a comment goes, ⋯ on a card, the names after "@", the list of comments and the control of the model and effort close when a click lands outside them; a click outside the card that closed a menu does nothing else (the mousedown in `remarks.js`, `RunPick` in `tools.js`).
- **A file tab stays where it is**: new data for the same file with the same lines asked for (a comment saved, an answer) draws it again where he scrolled to, not at the lines that it opened at (`Code.left` in `page.js`, `drawCode()`).
- **Resolve, calmly**: ✓ on a card shrinks and fades the card and the mark of its thread (`leave()` in `remarks.js`, `cb-leave` in `look.css`; at once with "reduce motion"). New data where only the comments changed draws nothing again, on Home, on the page of a change and in a file tab (`onlyCommentsChanged()` in `page.js`): the marks, the list and the open card follow (`Remarks.repaint()`), so saving, answering or resolving a comment does not make the page blink, and the code stays where he scrolled to.
- **Comments with no change file**: on a branch with no change file a comment on code is a comment of the repo, as one on the map is, in a file tab and on the page of the open branch (`filePage()` and `branchPage()` with the connected apps, `noChange` and `saveRepoRemark()` in `change-page.ts`): it goes to a new session or a known one, in the open folder, and ✓ resolves it. These pages show the threads of the repo on files (`repoRemarksOnFiles()`), Home the others. The page of the open branch loads again when such a comment changes, and turns into the change once an agent writes its change file.
- **The card** (`drawCard()` in `remarks.js`, class `cbox card`): a click on a mark, or on code lines with a thread, opens it beside its thing, not over it when there is room at its right or left; else over the side with more room, under or above the thing (`placeCard()`). A quiet head names the place in a few words ("Desk screen", "hold_service.py · lines 253–258", "mira-k · message"; the full words in its tooltip) and has ✓ Resolve, ⋯ for the less used actions ("Open the session", "Start a run") and ✕ Close. The thread shows as a small chat: his own words at the right in a tinted bubble, the agent at the left with its icon and name, the exact time in a tooltip; then the state line (`States.remarkLine()`), in the words of the picker and with the model and the effort that the comment was sent with ("waiting for Claude Code · this session · Start a run · Opus 5.5 · Extra"; "Claude Code · this session is working · 4 min · session", how long as a relative time with the exact time in its tooltip); then the box "Write a reply…" with the picker. Several threads on one thing stand one under the other, and the box answers the newest ("Reply" on another one moves it there). Escape and a click outside close the card; a new comment with text asks first. While the card of code lines is open, the lines have a soft tint.
- **Writing**: Cmd+Shift+. turns the pointer into a comment icon; Esc, or the key again, turns it back, and no hover window opens meanwhile. The next click opens the same card, empty, beside the thing or code line under it (lines selected before the key stay the target), with the cursor in its box. A click outside an empty card closes it; with text in it, "Discard this comment?" asks first, with "Discard" and "Keep writing". Enter or Cmd+Enter sends where the picker says; Shift+Enter makes a new line; Esc closes. After the send the card stays open on its new thread and the mark shows at the place, with no movement.
- **The picker** under the box says where the comment goes: "Send to <icon> Claude Code · this session" (`sendChoices()`, `choiceWords()` and `startChoice()` in `states.js`). Under it one quiet line says the model and the effort of the run, "Opus 5.5 · Extra" (see "The model and the effort of a run"). Its menu lists each connected app in the order of `connectedApps()` (on the path, with the skills): "This session · made this change" when the change has a session of that app; the other sessions of that app that Apostil knows in this repo and that a run can continue in this folder, newest first, at most 3, with their name (or a short id) and "used 4 min ago" (`sendToOf()` in `page-data.ts`, from `Store.knownSessions()`); "New session". Each row says in faint words the model and the effort of its run (`runWords()`): a continued session the model and the effort that it last used ("Opus 5.5 · Extra"), a new session the model of the setting at High ("Haiku 5.5 · High"), OpenCode "OpenCode's own model". Then, on a page with a pull request that takes the comment, "The pull request on GitHub"; last, "No agent: keep it as a note". With no app connected it has GitHub (when it takes it), "No agent" and a quiet line to "Set up for agents". It starts at the choice of the thread for a reply, else at his last choice in this repo (`Store.lastRemarkTo()`), else this session, else a new session of the first connected app. A known session is the `RemarkTo` kind `session` (`{ app, kind: 'session', session, name }`): its run continues that session in its folder (`startRun()` in `agent-run.ts`), as `current` continues the session of the change, and the inbox of the session of the change leaves it out.
- **The list of comments** (`drawList()` in `remarks.js`, class `cml`): a chat bubble with the count of open threads stands beside the switch of views, only when there is a thread or an open point (`drawCount()`). A click opens a list under it, in the order of the page (`byPlace`): each row has the mark, the place in bold, the newest words on one line (an answer starts with the name of its app) and the state line. A click on a row closes the list, goes to the view that shows its thing (the change, the large view of a part's or a wider diagram, "Diffs", the code, the conversation), moves the surface to it, lights it for 1.6 seconds and opens its card there (`goToThread()`). Under the rows: "Open points n" shows the findings of the fresh check in the same list, in their groups (a click shows the place and opens a card whose reply is tied to that point), and "n resolved" shows the resolved threads with "Reopen". Escape and a click outside close the list. A file tab has no top bar, so no list: its code lines have their marks. A thing that the change file no longer holds says "no longer in the diagram" in its row and its card, with the title that it kept, and its row goes to its part, else its diagram.
- **The quick comment**: Enter after Cmd+Shift+., with no click, opens the card on the whole of what the page shows: the file of a file tab, the diagram in view, or the diagram of the change (`wholeView` in `remarks.js`). With lines selected, it opens on those lines. For a comment on a whole file the agent also gets the notes of the file with their lines and the diagrams that the file is in (`aboutInChange` in `shared/context.ts`).
- **A comment on any component**: under the comment pointer, the smallest thing under it has a quiet outline, and a click opens the card on it: a part; a file name inside a part (it wins over the part); "5 more files"; the box "In no part"; a node of any diagram, with or without code lines; an arrow with its label; a participant and a message of a sequence diagram; a state and a transition of a state diagram; the diagram as a whole, on its title row or an empty place of its surface (a part wins over the diagram); on "Diffs" the head of a file and a line in the file now; in a file tab and in a hover window a code line, a note and a test (a hover window that the pointer is in stays when the key is pressed); a message of a pull request. The card names the thing in plain words, as `Arrow "API" to "Service"`. The same holds in the large view of a part's diagram and of a wider diagram, and in a part's diagram kept whole after drill up. `media/places.js` makes every target and says where it is: each drawing marks its things with `Places.mark()` (the target in `data-remark`, a key in `data-rk`), with the ids of the Mermaid text that `page-data.ts` reads with `diagramGraph()`.
- **The session of a thread**: a running or answered thread has the link "session". It opens the session in its app when the app has a link of its own (`sessionLink()`), else a terminal of VS Code in the folder of the change that continues it (`openSessionCommand()`: `claude --resume <id>`, `codex resume <id>`, `opencode --session <id>`). This is the one way to open a session (`sessionOpens()` in `shared/agents.ts`, `openAgentSession()` in `change-page.ts`), also for the line of a map run and the line of words for an agent; never a page of claude.ai in the browser. Two places keep only the link of the app: the head of a session in the list (a session with no app link shows its name as text) and the line of a comment to a session that cannot be continued. A run that Apostil starts keeps the session that it reports (`setRunSession()`). An agent can resolve a thread with `apostil resolve <id>`; "N resolved" then says "resolved by Claude Code".
- **What the agent gets with a comment**: the thing (its title, kind, file and lines, a step's note), and for a thing of a diagram the diagram as text, one line for each box and each arrow, at most 80 lines and one line for those left out (`diagramText()` in `shared/comment-lines.ts`; a drawn process of Home is made from the map by `mapDrawing()`, because its step ids such as `s21` change when the map is written again). A comment keeps the title, diagram, file and lines of its thing (`kept` in its target, saved by `withKept()`); when the thing is gone or names another thing, the agent gets one line that says the map was written again and what the comment was put on, and the card shows the kept title.
- **Rights of a comment run**: a Claude Code run that a comment starts has `Read`, `Grep`, `Glob`, `Edit`, `Write` and `Bash(apostil *)`. The setting `apostil.commentRuns` ("read and edit", the default, or "read only": no `Edit`, `Write` or `NotebookEdit`) sets it. Antigravity passes `--mode accept-edits` with `--settings` allowing `write_file(*)` and `command(apostil *)` (or denying `write_file(*)` in "read only"). Codex keeps its sandbox.
- **The model and the effort of a run**: one source of models for each app, `shared/models.ts`, read and never written. Claude Code: its own catalog of models (`~/.claude/cache/model-catalog/`, the section "main"); each family (Haiku, Sonnet, Opus, Fable, smallest first) with its name and its efforts, and a run gets the name of the family (`--model haiku`). ## More of the page

- **A link that has an agent do it**: no page asks the person to give words to an agent or to copy them; one direct link starts the work. That is the line of a pull request with no stored change: "This pull request has no description of Apostil yet. Describe it with a new Claude Code session". The words for the agent ("Describe pull request #35 for Apostil", `describeWords()`) ride in the link for VS Code alone and never show. The link names the session that will do it, so that nobody is surprised: "Describe it with the session of this change" (on the page of a change: the session that made it, as `@claude-current`), "Describe it with Claude Code session \"<name>\"" (elsewhere: the newest session that Apostil knows in this repo, of a stored change or of a run that it started, that a run can continue and whose app is installed; `Store.knownSessions()`), or "Describe it with a new Claude Code session" (none: the app of `appToStart()`); the tooltip says why. After the link stands the quiet line of the model of the run, "Sonnet 5.5 · Max" (see "The model and the effort of a run"). A session cannot continue in another folder, so for a pull request only a known session whose folder has its head branch checked out counts; a session on `main` does not, and the link says "a new … session". `askTo()` and `askPress()` in `shared/ask.ts` choose it, `askView()` and `startAsk()` in `ask-run.ts` give the page what to show and start the run (message `askAgent`). With no app that can be started, the line links to the pages that install Claude Code or Codex (`INSTALL_LINKS` in `media/tools.js`), as Home does. A run continues the session in its folder (`resumeCommand()`) or starts a new one (`newRunCommand()`; a new Claude Code session gets its id with `--session-id`, so that its link is there at once; Codex and OpenCode report theirs on their output). **Apostil checks the branch out, not the agent** (`pullFolder()` in `pull-folder.ts`): the run works in a folder with the head branch of the pull request checked out. Apostil first gets the commits of the pull request when the clone lacks them (`fetchPullCommits()`). A local branch of that name counts only when it holds the last commit of the pull request (`holdsHead()`): one without it is another branch (a pull request from a fork, often `main`) or one that is behind, and then no run starts and the line says so. A worktree of the repo that has the branch (`git worktree list --porcelain`) is that folder, and Apostil makes nothing. Else Apostil adds a worktree in its store, `worktrees/<repo>-pr-<n>`: with the local branch as it is, else with a new branch at the last commit of the pull request. Git notes where a branch was made, and `baseOf()` reads that note as the base of the change, so the new branch is made where the pull request left its base and then moved to its last commit; else `apostil material` would see no change. It never moves, resets or deletes a branch that was there before. The skills that `apostil setup` put into the repo for this repo only are not in Git, so the worktree gets a copy where Git ignores it. When Apostil cannot get the commits (no network, a fork with no access), no run starts, and the line says why in one sentence with the press again ("Could not check out the branch … of pull request #35: …"; `problem` of the view, kept while VS Code runs), with no toast. The words of the run get one sentence: "The branch of the pull request is checked out in this folder." (`ON_BRANCH`); the key of the record stays `describeWords()`. When the run ends (done or stopped), Apostil removes a worktree that it made (`git worktree remove --force`, only in its own folder of worktrees), so that the branch can be checked out in his own folder again; the branch stays, as `gh pr checkout` leaves one. A worktree in that folder that a run left (VS Code closed while it ran) is used and removed at the next press for that pull request. The stored change of that run then reads Git in the open folder (`changeWhere()`), and "Open the session" opens a terminal there. Codex and OpenCode get the same folder; Codex may write in the store (`codexRights()`). Its rights are what the skill `apostil-describe-change` runs (`describe` in `claudeRights()`): what reads the repo (`READ_REPO`), `Write` (its drafts) and `Bash(apostil *)`, and no `Edit` or `NotebookEdit`, and never `git worktree`, `git fetch` or `git checkout`; Codex keeps its sandbox. A command that it was not allowed ends the run with the toast and "Allow and try again". The store keeps one record for the words of a repo (table `ask_run`, `AskRun`), and it counts for `appToStart()` as a run that Apostil started. After the press the line says "Description by a new Claude Code session 1a2b3c4d · working · Open the session", then "done", or "stopped" with the press again; "Open the session" opens it the one way (message `openAskSession`). The page gets the record with its data (`ask`) and each change of it as the message `asked`, which draws only the line. A second click while it works starts nothing.

## The checks: `npm run check`, under 2 minutes

`npm run check` runs every check, and it must finish in under 2 minutes on the owner's Mac: it fails by itself when the total passes 2 minutes, so no change can slow it down unnoticed. Keep the checks few (one check for one behaviour, at the cheapest level: a unit test for logic, a browser check for drawing, pointer and keys, the window run only for what needs VS Code itself) and wait for a state, never for a fixed time.

It takes the window lock first (one check window at a time on a Mac: the folder `apostil-vscode-window.lock` in the temporary folder, or the one that `APOSTIL_WINDOW_LOCK` names; a lock older than 30 minutes with no check window is taken away), builds once, and then runs at the same time:

| Part | What it checks | Needs |
|---|---|---|
| unit tests | `node --test "out/**/*.test.js"`: the logic, the store, the command line (called inside the test program; three tests start the real program, for standard input, the inbox hook and writers at the same time). | Node |
| browser groups | `view/browser/<group>.mjs`, each a program with its own headless browser: the pages of `view/media` as files, with the drawing, the pointer, the keys and the themes. | Playwright |
| window | `view/window-check.mjs`: one start of a real VS Code window, one part after the other (below). | Playwright, VS Code |
| package check | `out/view/package-check.js`, after the window: the `.vsix` of this build, installed into a VS Code of its own with a home folder and a path of its own. | VS Code |

The unit tests and the browser groups run with a lower priority (`nice`), because a busy Mac slows the real window most. The run prints the count and the time of each part and the total, and keeps all that each part printed in `apostil-check/` in the temporary folder. `npm run check -- --pictures [<folder>]` takes the pictures that a person looks at, at double size; a failed check always takes one (`failed-<group>-<n>.png`). `APOSTIL_TIMES=1` shows when each check of the window run ended. No check reads the catalogs of models or the sessions of the agent apps in the real home: `npm run check` and `npm test` set `APOSTIL_AGENT_HOME` to an empty folder, the window run does the same when it runs alone, and the tests and the example data that need models make a made-up home (`madeUpAgentHome()` in `shared/test-repo.ts`).

A part alone: `npm test`; `node view/browser-check.mjs [--group <name>] [--pictures] [<folder>]`, or one group with `node view/browser/<group>.mjs`; `node view/window-check.mjs` (take the window lock yourself); `npm run package && npm run check-package`. Build first.

**Adding a check.** A unit test goes into a `*.test.ts` file (a new file is picked up by itself). A browser check goes into its group; a new group is a new file in `view/browser/`, which `view/browser-check.mjs` picks up by itself (its helpers stand in `HELPERS` there). A check in the real window is a step of `view/window-check.mjs`, only for what a page alone cannot show.

**The window run**, in its order, on the made-up example with its own settings, store and stand-ins for `gh`, `claude` and `codex` (nothing calls GitHub or starts an agent; its terminal is `/bin/cat`): the first start with Home in place of the empty editor area, the set-up question and the question of a new repo, a run of the map that was refused a command and "Allow and try again", which saves the map; Home when the last tab closes, the terminal that keeps the keyboard, and the setting off; the notes beside the code in the editor (the hover, find and typing, the real Cmd+Shift+,, edits that move a note, "off", and "tab" with a file that opens at a line and the key back at the line of the cursor); **A real pull request in a browser**, read only, for a look with your own eyes:

```bash
npm run build
node out/view/pull-request-data.js https://github.com/owner/repo/pull/12 26h
```

The second argument is when he last looked: hours back (`26h`), a time, or `never`. The third is the file name next to `page.html` (default `pull-data-12.js`, the name that a click on another pull request of a stack opens; `pull-data*.js` is not in Git). The command prints the address to open in a browser: `file://<this folder>/view/media/page.html?pull=pull-data-12.js`.

**The settings of the check windows.** Every window that a check starts gets `CHECK_SETTINGS` of `shared/run-in-vscode.ts`: `apostil.homeWhenEmpty` is off. `runInVsCode()` writes them; `view/window-check.mjs` turns the setting on for its first part and off again.
